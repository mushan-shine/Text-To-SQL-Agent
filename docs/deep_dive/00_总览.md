## 1. 项目要解决的问题

企业里的 Text-to-SQL 有两个现实难点：

1. **一次生成很难对**。数仓表多（BEAVER dw：97 张表、1,530 列），表名相似，关联路径不直观，业务口径藏在历史查询里。本项目基线：glm-4-flash 一次生成在 89 道评测题上只答对 2 道。
2. **线上没有标准答案**。用户问的问题没有 Gold，系统不能靠"对答案"判断自己错了没有。

所以项目的核心不是"写一个更好的 prompt"，而是 **Loop Engineering**：设计一个能在运行时自我修复（内循环）、并能从失败中持续学习（外循环）的系统，而且每一步都能被度量。

## 2. 整体设计原理

### 2.1 两个循环

```
            ┌──────────── ⑤ 外循环（离线，可以用 Gold，只用训练集 / 开发集）────────────┐
            │  抽题跑系统 → 对照 Gold 找错因 → 归纳候选知识 → 开发集逐条门禁 → 人工审核  │
            └───────────────┬──────────────────────────────────────▲───────────────┘
                 知识（只读）│                                      │ trace、错因、用户反馈
┌────── ③ 生成端 ───────────▼───┐    ┌──────────────── ④ 内循环（在线，不接触 Gold）──┐
│ 检索表 → 组装上下文 → 生成 SQL │───▶│ 执行 → 自检 → 观察 → 诊断 → 路由 → 修复 → 再执行 │
└───────────────────────────────┘    └──────────────────────┬──────────────────────────┘
                                                            │ 最终答案
                          ⑥ 评测：Loop 结束后对照冻结的 Gold 判分（只在离线实验中）
                          ⑦ 可观测：trace / MLflow / Console / 提问页 / 审核页
            ② 平台层：Databricks SQL Warehouse · Unity Catalog · Delta · App
            ① 数据底座：BEAVER → MySQL 参照 → 复制到 Delta → 方言适配 → 冻结 Gold
```

- **内循环负责"这一题"**：修的是显式失败（报错、空结果、结构性错误）。它看不到 Gold，线上也能跑。
- **外循环负责"下一题"**：从一批题的失败中归纳数仓约定，写进知识层，让系统少犯同类错误。
- **知识层是两个循环的接口**：外循环写、生成端和内循环读。

### 2.2 贯穿全项目的五条原则

| 原则 | 含义 | 在代码里的体现 |
|---|---|---|
| **Gold 隔离** | 运行时组件永远拿不到当前题的标准答案 | Agent 只收 `AgentTask`（[dataset.py:30](../../benchmark/beaver/dataset.py#L30)）；Observer 白名单（[observer.py:16](../../loop_engineer/observer.py#L16)）；技能禁止 import benchmark / evaluation（`tests/test_phase5.py`） |
| **数据三分** | 训练集学习、开发集衡量、评测集冻结后才跑 | 示例库 / 知识库排除评测集和开发集；外循环只在开发集做门禁；网页锁定评测集（`SHT_ALLOW_EVAL=0`） |
| **可复现** | 同一配置跑两次结果一致 | 贪心解码 + prompt 指纹缓存（[llm.py:240](../../agent/llm.py#L240)）；固定种子；版本号写进运行元数据 |
| **用数据做决定** | 新方法先离线测"抓错率 / 误报率"或在开发集对照，有效才接入 | `scripts/verifier_eval.py`、`judge_eval.py`、`validator_eval.py`；外循环门禁 |
| **能用代码就不用 LLM** | 规则诊断、确定性修复、数值检查都不调模型 | [diagnose.py:83](../../loop_engineer/diagnose.py#L83)、[schema_search.py:39](../../skills/schema_search.py#L39)、`checks.check_numeric` |

## 3. 端到端数据流

```
HuggingFace（BEAVER，需申请）
  ├─ beaver-query：5,787 道 dw 题（问题 + Gold SQL + 标注）──┐
  └─ beaver-table：表结构 + 样例值；beaver_db.zip（MySQL dump）│
                                                              ▼
① data/beaver/dw/dev.json（本地只读快照）      MySQL 参照库（本机）
     │ 种子 77 抽 100 题                           │ 逐表 → Parquet → Volume → Delta
     ▼                                             ▼
  benchmark.cases（原文 + 指纹）          self_healing_text2sql.dw（97 张表，421,707 行）
     │ 兼容性验证 + 规则适配 + 3 次稳定性
     ▼
  benchmark.gold_results（89 PRIMARY，冻结）
                                                              
③ runs/phase1/schema_dw.json（Agent 可见的表结构）           ⑤ 离线产出的知识
   app/bundle/examples_pool.json.gz（5,508 道相似题示例库）     runs/knowledge/kb.json（统计出的使用说明）
                                                              experience.knowledge_items（审核通过的知识）
        └──────────────┬───────────────────────────────────────┘
                       ▼
④ 每道题：LoopController.run → 每次尝试一条记录（SQL、执行、自检、诊断、修复）
                       │
                       ▼
⑥ 判分（离线实验）   evaluation.evaluation_results / runs      ← 对错只放这里
⑦ 可观测            traces.execution_traces、MLflow、Console   ← Agent 可见的过程
   产品             experience.user_queries / feedback → ⑤ 外循环 → experience.proposals → 审核 → knowledge_items
```

## 4. 项目价值（面向求职）

| 维度 | 体现 |
|---|---|
| **工程完整度** | 数据接入、平台、Agent、自我修复、学习闭环、评测、可观测、产品页面、部署，一条链路全部打通并上线（Databricks App） |
| **方法论** | 每一个设计都有对照实验或离线评估支撑，包括"不做什么"的负面结论（如 LLM 裁判误报 31/33，不接入） |
| **企业落地思维** | 用户问题没有 Gold → 只走内循环；改动先过开发集门禁，再由数据工程师审核；知识可回滚 |
| **诚实的度量** | 恢复率和误伤率并列；"自检通过"与"答对"分开展示；上界实验单独标注 |
| **可讲的故事** | 从"一次生成只对 2/89"出发，定位瓶颈（选表），用示例库和知识把 glm 在开发集上从 0/30 提到 5/30，把问题拆成内循环修显式失败、外循环学隐式约定 |

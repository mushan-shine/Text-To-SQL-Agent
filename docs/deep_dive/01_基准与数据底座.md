# ① 基准与数据底座

> 一句话：把 BEAVER 搬进 Databricks，并**证明**"在 Databricks 上判分"和"在官方 MySQL 上判分"是同一回事。
> 入口命令：`python scripts/phase0.py all`（分步：`env` → `import` → `replicate` → `compat` → `gold` → `report`）。

---

## 1. 设计原理与价值

### 1.1 要解决的问题

BEAVER 是企业数仓 Text-to-SQL 基准，官方执行引擎是 **MySQL**；本项目的运行平台是 **Databricks**。直接把 Gold SQL 放到 Databricks 上跑会遇到三类问题：

| 问题 | 例子 | 后果 |
|---|---|---|
| 方言不同 | MySQL `STDDEV()` 是总体标准差，Databricks `stddev()` 是样本标准差 | Gold SQL 能跑，但答案不同 |
| 语法不兼容 | MySQL 允许 `ROW_NUMBER() OVER (... ROWS ...)`，Databricks 报错 | Gold SQL 跑不了 |
| 数据复制失真 | MySQL `_ci` 排序规则不区分大小写；零日期；无符号整数 | 同一条 SQL 在两个库上结果不同 |

如果不先解决，后面所有"准确率"都不可信：模型答错可能是方言问题，答对也可能是巧合。

### 1.2 设计原则

1. **原始 Gold 不改**：`benchmark.cases` 保存 BEAVER 原文，带 SHA-256 指纹，重复导入不一致就拒绝覆盖。
2. **改写必须有依据、必须验证**：只允许两条有 MySQL 官方文档依据的规则；改写后的 SQL 必须在 Databricks 上跑出和 MySQL **相同的结果**才算通过。
3. **结果说了算**：判断"兼容"看执行结果，不看"能不能跑"。能跑但结果不同也是不兼容。
4. **不能用的就排除并计数**：结果依赖并列值排序（不确定）的题直接排除，写明原因。

### 1.3 价值

- 得到 **89 道可信的评测题**（PRIMARY：原始 46 + 规则改写 43），排除 11 道并记录原因（决策 D1，方案 B）。
- 冻结后的 Gold 结果换新连接重跑 3 次，**漂移 0**，保证后续实验可复现。
- 面试价值：说明你懂"**先验证度量本身，再去优化指标**"。很多项目直接跑基准，这一步能体现工程严谨性。

## 3. 各模块的设计原理与代码实现

### 3.1 数据模型：把"Agent 能看的"和"Gold"从类型上分开

**原理**：Gold 隔离不能靠"大家注意别用"，要靠类型。Agent 相关的函数签名只接收 `AgentTask`，拿不到 Gold 字段。

**实现**：[dataset.py:30](../../benchmark/beaver/dataset.py#L30)

```python
@dataclass(frozen=True)
class AgentTask:          # Agent 唯一能收到的东西
    case_id: str
    question: str
    db: str

@dataclass(frozen=True)
class BeaverCase:         # 含 gold_sql、gold_tables、join_keys、domain_knowledge ……
    ...
    def agent_view(self) -> AgentTask:          # dataset.py:75
        return AgentTask(case_id=self.case_id, question=self.question, db=self.db)

    @property
    def source_sha256(self) -> str:              # dataset.py:79，原始记录指纹，拒绝静默覆盖
```

- `to_row()`（[dataset.py:84](../../benchmark/beaver/dataset.py#L84)）把嵌套标注编码成 JSON 列，写入 `benchmark.cases`。
- 导入时还建了一个视图 `benchmark.cases_agent_view`，只暴露 `case_id, question, db`（[phase0.py:75](../../benchmark/beaver/phase0.py#L75)）。

### 3.2 加载与抽样：和官方完全一致

**原理**：评测样本必须和 BEAVER 官方 `dev_sampled.json` 相同，结果才能和论文对比。

**实现**：[loader.py:22](../../benchmark/beaver/loader.py#L22)

```python
def sample_official(entries, sample_size, seed=77):
    random.seed(seed)                     # 与 BEAVER data/download_hf.py 相同
    return random.sample(entries, min(sample_size, len(entries)))
```

- `load_from_huggingface`（[loader.py:28](../../benchmark/beaver/loader.py#L28)）：数据集需要在 HuggingFace 上申请（gated），字段映射照抄官方脚本。
- 第一次下载后 `save_local_snapshot`（[loader.py:82](../../benchmark/beaver/loader.py#L82)）存成 `data/beaver/dw/dev.json` 和 `dev_tables.json`，之后全部从本地读，保证离线可复现。
- `load_cases`（[loader.py:64](../../benchmark/beaver/loader.py#L64)）检查抽样结果没有重复 id。

结果：从 dw 全部 5,787 题中抽 100 题（复杂查询 43、领域复杂查询 48、领域查询 9）。

### 3.3 数据库复制：MySQL → Delta，逐列核对

**原理**：
- **复制整个库，不是只复制 Gold 用到的表**。只复制 Gold 表等于把答案泄露给检索。
- **库名保持一致**：MySQL 库 `dw` → Unity Catalog schema `self_healing_text2sql.dw`，Gold SQL 不用改表名就能跑。
- **核对用"画像"**：每列比较非空数和不同值个数，而不是逐行比。

**实现**：编排在 [phase0.py:94](../../benchmark/beaver/phase0.py#L94) `replicate_databases`，每张表：

```
MySQL information_schema 读列定义           phase0.py:86  mysql_columns
  → map_column 决定 Databricks 类型          replicate.py:57
  → write_parquet（分批读，逐值转换）         replicate.py:142
  → upload_file 到 Volume                    dbx/catalog.py:70
  → CREATE OR REPLACE TABLE（显式 DDL）      replicate.py:169
  → INSERT ... SELECT CAST(...) FROM read_files(parquet)   replicate.py:177
  → 两个引擎各跑 profile_sql，compare_profiles 比较          replicate.py:190 / 223
  → 写 benchmark.replication_report
```

类型映射的关键决定（[replicate.py:57](../../benchmark/beaver/replicate.py#L57) `map_column`）：

| MySQL | Databricks | 原因 |
|---|---|---|
| `varchar` 等，排序规则 `*_ci` | `STRING COLLATE UTF8_LCASE` | 复现 MySQL 不区分大小写的比较 |
| 无符号整数 | 放宽一级（INT → BIGINT） | 保证取值范围装得下 |
| `datetime` | `TIMESTAMP_NTZ` | MySQL DATETIME 没有时区，避免会话时区偏移 |
| `decimal(p>38)` | `DECIMAL(38, s)`，以字符串暂存再 CAST | Databricks 精度上限 38 |
| `time` | `STRING`（HH:MM:SS） | Databricks 没有 TIME 类型 |

零日期（`0000-00-00`）在 `stage_value`（[replicate.py:107](../../benchmark/beaver/replicate.py#L107)）里转成 NULL 并计数，核对时作为容差。

结果：97/97 张表、421,707 行全部一致；95 张表逐列一致；2 张表 3 列有 8 个值差异。原因是 MySQL `utf8mb4_0900_ai_ci` **不区分重音**（`Gödel` = `Godel`），而 `UTF8_LCASE` 只忽略大小写。这 3 列没有被任何评测题的 Gold SQL 使用，不影响评测。

### 3.4 兼容性验证：按结果分类

**原理**：原始 Gold SQL 不改，在 MySQL（官方引擎）和 Databricks 上**各跑 3 次**（关闭结果缓存）。只有"能跑 + 结果一致 + 结果稳定"才算 `COMPATIBLE`。

**实现**：[compatibility.py:174](../../benchmark/beaver/compatibility.py#L174) `validate_case`

```python
ref  = run_repeated(reference, case.gold_sql, case.db, repeats)   # MySQL，3 次
cand = run_repeated(candidate, case.gold_sql, case.db, repeats)   # Databricks，3 次
cmp  = cross_engine_match(cand.rows, ref.rows)
# 判定顺序：
#   MySQL 都跑不了        → REFERENCE_FAILED（不能当 Gold）
#   Databricks 报错       → 按错误类别分 SYNTAX / FUNCTION / SCHEMA / SEMANTICS（classify_error，:55）
#   任一引擎结果不稳定     → INCOMPATIBLE_SEMANTICS（非确定结果不能当 Gold）
#   结果集合一致           → COMPATIBLE
#   能跑但结果不同         → INCOMPATIBLE_SEMANTICS
```

- `run_repeated`（[compatibility.py:129](../../benchmark/beaver/compatibility.py#L129)）对每次结果算 `result_hash`，3 个指纹相同才算稳定。
- `static_hazards`（[compatibility.py:74](../../benchmark/beaver/compatibility.py#L74)）用 sqlglot 标出潜在风险（`LIMIT` 无 `ORDER BY`、整数除法等），只作信息记录，判定仍以执行结果为准。

结果：不改直接能跑 94/100，但**结果与 MySQL 一致只有 46/100**。"能跑就算兼容"会严重高估。

### 3.5 跨引擎比较：同一个值，不同的表示

**原理**：两个驱动会把同一个值表示成不同形式。MySQL 的 `AVG(int)` 返回 `DECIMAL 6.8333`，Spark 返回 `DOUBLE 6.833333…`。逐字比较会误判。

**实现**：[evaluator.py:149](../../benchmark/beaver/evaluator.py#L149) `cross_engine_value_equal`

```python
# 一方是 DECIMAL：按它自己的小数位比较，差值 ≤ 最后一位的一半即相等（MySQL 的 AVG / 除法保留 4 位）
half_ulp = Decimal(5).scaleb(-min(scales) - 1)
return abs(da - db) <= half_ulp * (1 + Decimal("1e-9"))
# 两边都是浮点：相对误差 1e-6
return math.isclose(float(a), float(b), rel_tol=1e-6, abs_tol=1e-9)
```

`cross_engine_match`（[evaluator.py:231](../../benchmark/beaver/evaluator.py#L231)）先按非数值列分桶，桶内做配对。大桶（> 200 行）先排序再对齐，复杂度从 O(n²) 降到 O(n log n)。这是实际遇到的问题：dw_4004 返回 15,881 行，原算法要比较约 2.5 亿次，卡了 20 分钟（问题记录 #6）。

同一文件里还有**官方 EX 比较** `official_match`（[evaluator.py:40](../../benchmark/beaver/evaluator.py#L40)），逐行移植 BEAVER `ex_acc.py`：值转字符串，比较行集合，列顺序有意义、列名忽略。它用于后续实验：Gold 和生成结果都来自 Databricks，同一引擎。

### 3.6 规则适配：只改有文档依据的地方

**原理**：不用 sqlglot 自动转换方言。自动转换改动面大、无法解释，所以只允许**两条**有 MySQL 官方文档依据的规则。改写是在原文上精确替换字符串片段，改写前后的差异正好就是规则本身。

**实现**：[adapter.py:40](../../benchmark/beaver/adapter.py#L40) `RULES`、[adapter.py:133](../../benchmark/beaver/adapter.py#L133) `apply_rules`

| 规则 | 改什么 | 依据 |
|---|---|---|
| `mysql_population_statistics` | `VARIANCE()` / `STD()` / `STDDEV()` → `VAR_POP()` / `STDDEV_POP()` | MySQL 文档：这些是总体统计的同义词 |
| `nonaggregate_window_frame_ignored` | 删除 `ROW_NUMBER / RANK / LAG …` 上的 `ROWS/RANGE` 窗口帧 | MySQL 文档：对非聚合窗口函数，帧子句被忽略 |

- 定位用 sqlglot 的**分词器**，跳过字符串字面量和 `t.std` 这种限定名（`_is_call`），不会误改。
- `try_adapt`（[adapter.py:155](../../benchmark/beaver/adapter.py#L155)）：改写后在 Databricks 跑 3 次，结果与 MySQL 一致且稳定才标 `RESULT_EQUIVALENT`。
- 改写记录存 `benchmark.gold_adaptations`（原文、改写后、规则名、文档链接、验证结论），原始 Gold 不动。

结果：43 条改写后结果一致（总体方差规则 38、窗口帧规则 5）。

`apply_rules` 后来被多处复用：开发集构建、few-shot 示例、相似题示例库、数仓使用说明统计，都先把 MySQL Gold 转成 Databricks 能解析的形式。

### 3.7 冻结 Gold：换新连接复跑，检测漂移

**原理**：兼容性阶段已经证明"与 MySQL 等价"。冻结时换一个**新的数据库会话**再跑 3 次，必须复现兼容性阶段记录的指纹，否则判为漂移并排除。

**实现**：[phase0.py:201](../../benchmark/beaver/phase0.py#L201) `build_gold_results`

```python
if status == COMPATIBLE:          sql, eligibility = case.gold_sql, "PRIMARY"
elif case.case_id in adapted:     sql, eligibility = adapted_sql, "PRIMARY"   # 决策 B：验证过的改写也进主评测
else:                             eligibility = "EXCLUDED"（写明原因）
runs  = run_repeated(dbx, sql, case.db, repeats)
drift = runs.status != "SUCCESS" or not runs.stable or runs.result_hashes[0] != expected
gold_result = serialize_rows(runs.rows)       # 规范化 JSON，之后判分直接用
```

写入 `benchmark.gold_results`：`gold_result`（规范化结果行）、`result_hash`、`evaluation_eligibility`（PRIMARY / SECONDARY / EXCLUDED）、`exclusion_reason`、`qualification_run_id`（追溯到哪次兼容性运行）。

### 3.8 报告：从证据文件自动得出结论

[report.py:17](../../benchmark/beaver/report.py#L17) `decide_architecture` 按实测比例判定方案：

- **A**：≥ 95% 的原始 Gold 直接兼容；
- **B**：加上规则改写后 ≥ 70% 可用；
- **C**：否则，Databricks 评测只能作为独立环境。

本项目：46 直接兼容 + 43 改写 = 89/100 可用 → **方案 B**。报告里没有手填的数字，全部从 `runs/phase0/*.json` 读出。

## 6. 讲解要点

- "我没有直接在 Databricks 上跑基准，而是先证明两个引擎判分等价：94 条能跑，但只有 46 条结果一致。"
- "方言差异我只用两条有官方文档依据的规则处理，每条改写都在结果上验证，原始答案保持不动。"
- "不能保证确定结果的 11 道题直接排除并计数，而不是想办法'修'到能用。"

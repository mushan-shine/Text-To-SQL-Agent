# ② 平台层（Databricks）

> 一句话：给上层提供**统一、安全的 SQL 执行接口**，和**按权限边界划分的存储布局**。
> 上层（生成端、内循环、外循环、评测、页面）都只通过这一层接触数据库。

---

## 1. 设计原理与价值

### 1.1 为什么需要单独一层

项目里至少有 6 个地方要执行 SQL：Phase 0 核对、基线、内循环、外循环、验证子 Agent、网页。如果各自直接调驱动，会出现：

- 会话设置不一致（有的开 ANSI 模式，有的没开），同一条 SQL 结果不同；
- 有人不小心执行了写语句；
- 报错格式各不相同，诊断代码没法统一解析。

所以平台层做三件事：**统一执行**、**统一报错**、**统一存储**。

### 1.2 设计原则

| 原则 | 做法 |
|---|---|
| **引擎可互换** | MySQL 和 Databricks 执行器实现同一个接口 `execute(sql, db) -> ExecutionResult` |
| **生成的 SQL 默认不可信** | 只允许单条只读语句；限制返回行数；超时 |
| **报错是信息** | 从报错文本里抽出错误类别（如 `UNRESOLVED_COLUMN`），供诊断使用 |
| **存储按权限边界划分** | Gold、Agent 可见的过程、判分结果、产品数据分别放在不同 schema |
| **表结构只定义一次** | 所有 Delta 表的列定义集中在 `dbx/tables.py` |

### 1.3 价值

- **执行器是内循环的"传感器"**：Databricks 的报错是结构化的（错误类别、找不到的列、"Did you mean" 候选）。正因为平台层把这些信息完整保留下来，规则诊断才能不调用 LLM（[04](04_内循环Loop.md)）。
- **存储边界让 Gold 隔离可以被检查**：`traces` 里没有任何由 Gold 算出的字段，自检模式下的组件读 `traces` 也不会泄露答案。

## 3. 各模块的设计原理与代码实现

### 3.1 执行接口：统一结果、只读保护

**实现**：[base.py:13](../../execution/base.py#L13)

```python
@dataclass
class ExecutionResult:
    engine: str
    status: str            # SUCCESS | ERROR | TIMEOUT | REJECTED（Databricks 另有 TOO_MANY_ROWS）
    rows: list[tuple]
    columns: list[str]
    error: str | None
    error_class: str | None    # 引擎错误类别，如 UNRESOLVED_COLUMN
    elapsed_ms: int
```

只读检查 [base.py:41](../../execution/base.py#L41) `is_read_only`：

```python
stmts = sqlglot.parse(sql, read=dialect)
if len(stmts) != 1: return False                     # 只允许单条语句
return not any(isinstance(n, _WRITE_NODES) for n in stmts[0].walk())
# _WRITE_NODES：Insert / Update / Delete / Merge / Drop / Create / Alter / Command / Truncate
```

- 用语法树判断，不用关键字匹配，所以 `SELECT ... WHERE note = 'DELETE'` 不会被误拦。
- 解析失败时：以 `SELECT` / `WITH` / `(` 开头的放行（让引擎报语法错，这个报错对诊断有用），其余拒绝。

### 3.2 Databricks 执行器

**连接**：[databricks_sql.py:38](../../execution/databricks_sql.py#L38)

- 认证走 `~/.databrickscfg` 的 profile（本地），或 App 自己的凭据（线上）。
- 没有指定 warehouse 时自动发现，优先选正在运行的（`_discover_http_path`）。
- 连接建立后立即应用会话设置 [databricks_sql.py:29](../../execution/databricks_sql.py#L29)：

```python
SET ANSI_MODE = false            # 与 MySQL 一致：x/0 返回 NULL 而不是报错
SET STATEMENT_TIMEOUT = 120
SET use_cached_result = false    # Phase 0 测稳定性时必须关掉结果缓存
```

**两种执行方法，用途严格区分**：

| 方法 | 用途 | 安全检查 |
|---|---|---|
| `run(sql)`（[:85](../../execution/databricks_sql.py#L85)） | 项目自己的可信 SQL：建表、写入、查询 Delta | 无（代码里写死的 SQL） |
| `execute(sql, db, max_rows)`（[:106](../../execution/databricks_sql.py#L106)） | 模型生成的、Gold 的、用户修正的 SQL | 只读检查、行数上限、超时、报错解析 |

`execute` 的核心逻辑：

```python
if not is_read_only(sql, "mysql") and not is_read_only(sql, "databricks"):
    return ExecutionResult(self.engine, "REJECTED", error="not a single read-only statement")
if db != self._db:
    self.use(self.catalog, db)                 # USE CATALOG / USE SCHEMA dw
rows = cur.fetchmany(max_rows + 1)             # 多取一行，用来判断是否超限
if len(rows) > max_rows:
    return ExecutionResult(..., "TOO_MANY_ROWS")   # 防止笛卡尔积拖垮系统（默认 50 万行）
...
except Exception as e:
    cls = extract_error_class(str(e))          # "[UNRESOLVED_COLUMN.WITH_SUGGESTION] ..." → UNRESOLVED_COLUMN.WITH_SUGGESTION
    status = "TIMEOUT" if 超时 else "ERROR"
```

`TOO_MANY_ROWS` 本身也是诊断信号：结果爆炸通常说明关联键写错了，诊断器会把它判为关联问题（[diagnose.py:115](../../loop_engineer/diagnose.py#L115)）。

### 3.3 MySQL 执行器

[mysql.py:12](../../execution/mysql.py#L12)：接口与 Databricks 相同，额外提供：

### 3.4 Catalog 布局：一个 catalog，按权限边界分 schema

**实现**：[catalog.py:23](../../dbx/catalog.py#L23) `Layout`、[catalog.py:42](../../dbx/catalog.py#L42) `ensure_layout`

```
self_healing_text2sql                  （catalog；Free Edition 建不了时回退到 workspace）
├── benchmark      Gold 和基准资产：cases、gold_results、sql_compatibility、gold_adaptations、
│                  tables_meta、replication_report；volume `staging`（写入中转）
├── dw             BEAVER 数仓的 97 张表（生成的 SQL 在这里执行）
├── traces         Agent 可见的过程：execution_traces（每次尝试一行）、diagnoses
├── evaluation     判分和离线分析：evaluation_results、runs、failure_labels、diagnosis_eval
└── experience     产品和外循环：user_queries、feedback、proposals、knowledge_items
```

| schema | 谁写 | 谁读 | 含 Gold 信息 |
|---|---|---|---|
| `benchmark` | Phase 0 | 评测（判分）、离线分析 | ✅ |
| `dw` | Phase 0 复制 | 所有 SQL 执行 | 否（原始数据） |
| `traces` | 发布脚本 | Console、Observer / Diagnoser（离线评估时） | ❌ **禁止** |
| `evaluation` | 发布脚本、Phase 3/4 | Console、分析脚本 | ✅（对错、表召回） |
| `experience` | 提问页、外循环、审核页 | 外循环、审核页、生成端（只读 active 知识） | 训练集 / 开发集聚合结果，不含用户问题的 Gold（用户问题本来就没有 Gold） |

**关键边界**：`traces` 和 `evaluation` 物理上分开。`correct`、`eval_table_recall` 只写进 `evaluation`，不写进 `traces`（[tables.py](../../dbx/tables.py) 注释和测试保证）。

### 3.5 写 Delta：Parquet 中转，一次往返

**原理**：从本机逐行 `INSERT` 很慢。改为把整批行写成 Parquet，上传到 Volume，再用一条 SQL 读进 Delta。

**实现**：[catalog.py:84](../../dbx/catalog.py#L84) `write_rows`

```python
path = f"{layout.staging_root}/{schema}.{table}/{uuid4().hex}.parquet"
upload_bytes(runner.workspace_config, path, rows_to_parquet(rows, arrow_schema))
src = f"SELECT * FROM read_files('{path}', format => 'parquet')"
mode == "overwrite"        → CREATE OR REPLACE TABLE fq AS src
mode == "create_if_absent" → CREATE TABLE fq AS src            # 已存在就报错（benchmark.cases 用这个，防覆盖）
mode == "append"（默认）   → CREATE TABLE IF NOT EXISTS fq AS src LIMIT 0
                             ensure_columns(...)                # 新增字段自动 ALTER TABLE ADD COLUMNS
                             INSERT INTO fq BY NAME src         # 按列名插入，不依赖列顺序
```

- `ensure_columns`（[catalog.py:106](../../dbx/catalog.py#L106)）：只做加列，不删不改，所以旧运行的数据和新版本代码可以共存。
- `BY NAME`：Arrow schema 调整了列顺序也不会写错列。

### 3.6 表结构集中定义

[tables.py](../../dbx/tables.py) 用 Arrow schema 定义每张表的列和类型，例如 `EXECUTION_TRACES`、`EVALUATION_RESULTS`、`RUNS`、`GOLD_RESULTS`，以及产品化新增的 `USER_QUERIES`、`FEEDBACK`、`PROPOSALS`、`KNOWLEDGE_ITEMS`。写入时同一个 schema 既决定 Parquet 类型，也决定 Delta 的列。

## 4. 数据流转

```
                 上层调用                                    平台层                          Databricks
生成端 / 内循环 / 外循环 ─ execute(sql, "dw", max_rows) ─▶ 只读检查 → USE dw → 执行 ──▶ SQL Warehouse → dw.* 表
                          ◀─ ExecutionResult(status, rows, error_class) ─┘

发布 / 页面 / 外循环 ────── write_rows(rows, arrow_schema) ─▶ Parquet → Volume staging ─▶ read_files → Delta 表
                          ◀─ query_df(sql) / run(sql) ───────────────────────────────── traces / evaluation / experience
```

一次内循环尝试经过平台层的数据：

```
generated_sql ──execute──▶ status=ERROR, error="[UNRESOLVED_COLUMN.WITH_SUGGESTION] ... `sd`.`TERM_CODE` ... Did you mean ..."
                           error_class="UNRESOLVED_COLUMN.WITH_SUGGESTION"
                ──▶ Observer 从 error 文本解析：错误类别、找不到的列、别名、候选列（[04]）
```

## 5. 运维注意（Free Edition）

- **SQL Warehouse 和 App 的计算资源会因空闲或配额被自动停止**，页面打不开时先检查：

```bash
databricks warehouses start 0e96e1d4ab3f34b0 -p DEFAULT
```

```bash
databricks apps start self-healing-text2sql -p DEFAULT
```

- **表的所有者是"第一次创建它的身份"**。App 的服务主体先建的表（如用户在线提交反馈时创建的 `experience.feedback`），本机账号默认没有读权限，外循环读取会报 `INSUFFICIENT_PERMISSIONS`。外循环已改为读取失败时跳过反馈挖掘并记录警告；根本解决方法是由本机账号预先建表，或把表的所有权转给本机账号。

## 6. 讲解要点

- "所有 SQL 都走同一个执行器：只读、限行、超时、统一的报错解析。报错类别是后面规则诊断的基础。"
- "存储按权限边界分 schema。Agent 可见的过程放 `traces`，对错放 `evaluation`，从存储层面保证不串。"
- "写 Delta 用 Parquet + `read_files` 一次往返，加列自动演进，重复发布幂等。"

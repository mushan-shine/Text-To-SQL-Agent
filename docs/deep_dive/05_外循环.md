# ⑤ 外循环

> 一句话：**离线**从一批题的失败中归纳"这个数仓的约定"，经开发集门禁和数据工程师审核后写进知识层，让系统**下一题**少犯同类错误。
> 入口：`python scripts/build_knowledge.py`（全量统计知识）、`python scripts/outer_loop.py`（错误驱动的一次迭代）、网页「审核」页（批准上线）。

---

## 1. 设计原理与价值

### 1.1 为什么需要外循环

内循环只能修**显式失败**（报错、空结果、结构性错误）。错误分析显示，更大的问题是**能执行但语义错**（deepseek + 相似题示例 + Loop：21 道能执行但错）：

| 类别 | 占比 | 能否从数据中学 |
|---|---|---|
| A 选错表 / 用表不全 | 38% | ✅ 已解题里有"同类问题用哪些表" |
| B 关联方式 / 路径 | 19% | ✅ 已解题里有"这两张表怎么关联" |
| C 查询结构 | 19% | 部分（示例、更强的模型） |
| D 过滤理解 | 10% | 部分 |
| E + F 基准噪声、统计口径标注不一致 | 14% | ❌ 不作为目标 |

A + B 这 57% 是"**数仓使用约定**"，运行时的自检发现不了（题干本身不是可靠的规格），只能从已解题中学。这就是外循环的职责。

### 1.2 为什么不能把错题的原因直接交给内循环

错因是拿 Gold 比出来的。把它交给内循环，等于看答案改考卷：生产环境做不到，开发集也会失去衡量作用。正确做法是**从训练集学通用知识，在开发集上衡量**。

### 1.3 设计原则（企业做法：评测驱动 + 人在环路）

| 原则 | 做法 |
|---|---|
| **学习只用训练集** | 训练集 = dw 全部题 − 评测集 − 开发集（约 5,650 道），模拟企业的"已验证查询日志" |
| **学通用规律，不学单题答案** | 候选知识至少要有 2 道错题支持；关键词要在多道题里出现、并且确实指向那张表 |
| **每条知识附证据** | 支持度、错题 id、例题、错误 SQL |
| **不退步才推荐** | 门禁：答对不减少、零误伤、token 增幅 ≤ 20%；**逐条**回归；门禁题 = 从训练集另留、不参与挖掘的**验证集**（默认 200 题），建议批准的条目再在开发集上复核 |
| **人批准才上线** | 提案进"待审核"；数据工程师在审核页批准，下一次提问生效 |
| **可回滚、可追溯** | 停用 = 改状态，不删数据；谁、何时批准 / 停用都有记录 |
| **评测集不参与** | 只在配置冻结后做定期报告 |

### 1.4 两层外循环

| 层 | 学什么 | 怎么学 | 什么时候跑 |
|---|---|---|---|
| **全量统计** | 相似题示例库、数仓使用说明（kb.json） | 统计全部训练集的 Gold SQL，**不调用 LLM** | 数据变化时重建 |
| **错误驱动迭代** | 选表偏好、补表提示、关联规则、已验证查询 | 抽一批训练题**让当前系统答**，对照 Gold 找它具体错在哪 | 定期（按批） |

第二层是在第一层之上叠加：迭代时系统已经开着示例库和使用说明，找到的是**用了全量知识之后仍然会犯的错**。

### ② 当前系统作答并判分，给错题标错因

[outer_loop.py:83](../../evaluation/outer_loop.py#L83) `run_and_judge`

```python
with ThreadPoolExecutor(4) as pool:                   # LLM 调用并行
    generated = pool.map(retrieve + generate, cases)
for case, g in zip(cases, generated):                 # SQL 执行串行（同一个 warehouse 会话）
    ex = executor.execute(g.sql, db)

```

这里**只做第 1 次生成，不走修复**：外循环改进的是"生成端知道什么"，第 1 次尝试最能反映知识的效果。

### ③ 从错题归纳候选知识

四个挖掘函数，输出统一格式 `{kind, title, content, evidence}`：

| 函数 | 条件 | 产出 |
|---|---|---|
| `mine_table_preferences`（[:160](../../evaluation/outer_loop.py#L160)） | 生成用了表 X、Gold 用了表 Y，且 X、Y 是相似表（同一 kb 组，或列名 Jaccard ≥ 0.4），≥ 2 道题 | **选表偏好**：问到 {关键词} 时用 Y，不用 X |
| `mine_missing_tables`（[:191](../../evaluation/outer_loop.py#L191)） | Gold 用了表 T、生成没用，≥ 2 道题，且能找到关键词 | **补表提示**：问到 {关键词} 时还需要 T，关联键 K |
| `mine_join_rules`（[:221](../../evaluation/outer_loop.py#L221)） | 两张表都用了，但漏了 Gold 的关联条件，≥ 2 道题 | **关联规则**：A 与 B 用 K 关联（INNER / LEFT 取统计多数） |
| `mine_verified_queries`（[:243](../../evaluation/outer_loop.py#L243)） | 用户 👍 的答案；或 👎 且提供了**能执行**的修正 SQL | **已验证查询**（去重：同一问题只取一条） |

**冲突处理**（`resolve_conflicts`）：同一对表出现方向相反的选表偏好（"用 Y 不用 X"和"用 X 不用 Y"）时，支持度相差 2 倍以上保留多的一方，否则两条都丢弃并记录。第 3 次迭代就出现过 academic_terms 和 academic_terms_all 互相"优先"、支持度都是 3 的情况。

**关键词筛选**（[:133](../../evaluation/outer_loop.py#L133) `_keywords`），决定提示在哪些问题上触发：

```python
词要满足：
  - 在 ≥ 2 道支持题里出现（是规律，不是某一题的措辞）
  - 不含数字、不是数字词（"2021fa"、"12"、"five" 不行），至少 3 个字母
  - 在已解题统计里确实指向这张表：P(表 | 词) ≥ 0.5，且 ≥ 2 倍于该表的基础使用率
    （"least"、"description" 这种到处出现的词不行）
```

这是第 2 次迭代后的改进。之前的关键词里混进了 five、12、least、2021fa，提示在不相关的问题上也会触发，导致开发集误伤。

**为什么要"补表提示"**：第 1 次迭代只挖"用了相似表 X 而不是 Y"，结果 0 条候选。检查发现 glm 的选表错误几乎都是**漏表**（`academic_terms` 漏了 8 次），真正的相似表替换只有 1 例。挖掘规则要贴合模型实际犯的错。

### ④ 门禁：在验证集上逐条回归，开发集复核

[outer_loop.py:324](../../evaluation/outer_loop.py#L324) `gate_candidates`

```python
val = sample_training(queries, 评测集 | 开发集 | 挖掘样本, val_n=200, val_seed)   # 验证集：与挖掘样本不重叠
exclude = 评测集 | 开发集 | 挖掘样本 | 验证集                                     # 门禁题都不能当自己的示例
before = run_and_judge(验证集, generator(exclude, 当前系统))
reuse  = {case_id: result for result in before}
for 每条候选 c:
    after_c = run_and_judge(验证集, generator(exclude, 当前系统 + [c]), reuse=reuse)
    reg_c   = compare(before, after_c)
good = [c for c in 候选 if reg_c.gate_passed and reg_c.fixed]      # 单独通过且有提升
if len(good) >= 2:
    combined  = compare(before, run(验证集, 当前系统 + good))       # 合在一起再复核（知识之间可能互相影响）
if good:
    dev_check = compare(开发集当前, run(开发集, 当前系统 + good))    # 开发集复核
```

**为什么门禁从开发集换成验证集**：第 3 次迭代在 30 题开发集上逐条回归，每条只影响 5–19 题，原本答错的一题都没修好，而个别对 prompt 很敏感的题（dw_4867、dw_977）反复被误伤。30 题既看不出提升，也容易被个别题左右。验证集从训练集另抽 200 题，和挖掘样本、开发集、评测集都不重叠，会触发知识的题更多；开发集保留为最后一道复核。

`compare`（[:294](../../evaluation/outer_loop.py#L294)）：

```python
fixed    = 原来错、现在对的题
harmed   = 原来对、现在错的题
affected = prompt 因这条候选而改变的题
gate_passed = correct_after >= correct_before and not harmed and token_increase <= 20%
```

**逐条门禁的成本很低**：一条候选只会改变部分题的 prompt。prompt 没变的题直接复用 `before` 的结果（[:83](../../evaluation/outer_loop.py#L83) `reuse` 参数，按 prompt 哈希判断），不调 LLM、不执行 SQL；变了的题，LLM 回答又有缓存。

**为什么从"整批"改为"逐条"**：第 2 次迭代 9 条补表提示整批回归，开发集答对 5 → 4、误伤 1 题，整批被判驳回，好的条目也一起被否了。逐条回归能区分好坏，还能标出"开发集里没有会触发这条的题，回归无法验证"。

**建议**（[:314](../../evaluation/outer_loop.py#L314) `recommendation`，每条单独给出）：

| 情况 | 建议 |
|---|---|
| 门禁不通过 | 建议驳回 |
| 通过且有新答对 | 建议批准 |
| 通过，但开发集里没有题会触发它 | 中性：无法验证，由审核人判断 |
| 通过，没提升也没退步 | 中性 |
| 单独通过，但与其他建议批准的合用时不通过 | 中性：建议逐条批准并观察 |
| 验证集通过，但开发集复核有退步 | 中性：建议观察后再批准 |

### ⑤ 写成待审核提案

[outer_loop.py:341](../../evaluation/outer_loop.py#L341) `proposal_rows` → [experience.py:83](../../dbx/experience.py#L83) `save_proposals`

## 4. 审核与生效

### 4.1 状态流转

[dbx/experience.py](../../dbx/experience.py)

```
experience.proposals          pending ──批准──▶ approved      ──同时插入──▶ experience.knowledge_items（active）
                                      └─驳回──▶ rejected                                    │
                                                                                停用（回滚）▼
                                                                          knowledge_items（inactive）
```

- `review_proposal`（[experience.py:99](../../dbx/experience.py#L99)）：`UPDATE ... WHERE status = 'pending'`（防重复审核），批准时插入一条 active 知识，记录批准人和时间。
- `deactivate_item`（[experience.py:124](../../dbx/experience.py#L124)）：只改状态为 inactive，记录停用人和时间，不删数据。
- 所有 SQL 字符串值经 `sql_str`（[experience.py:33](../../dbx/experience.py#L33)）转义，含单引号的文本也不会出错。

### 4.2 如何生效

提问页和运行页每次运行时调用 `load_curated(conn, layout)` + `attach_curated(generator, ...)`（[app/runner.py:193](../../app/runner.py#L193) `build_controller`）。批准或停用都在**下一次提问**时生效，不需要重新部署。生效方式见 [03](03_生成端Agent.md) 第 3.5 节。

## 6. 迭代记录

| 迭代 | 设置 | 结果 | 带来的改进 |
|---|---|---|---|
| 第 1 次 | 训练 60 题（59 题 Gold 可执行），只挖相似表替换 | 训练答对 13/59；**候选 0 条** | 发现 glm 的选表错误是"漏表"而不是"换错表" → 新增补表提示 |
| 第 2 次 | 同一批，加补表提示，整批回归 | 9 条补表提示；开发集 5 → 4，误伤 1，**整批驳回** | 关键词噪声大（five、12、least）→ 关键词筛选；整批无法区分好坏 → 逐条门禁 |
| 第 3 次 | 训练 200 题（193 题 Gold 可执行），新关键词筛选 + 逐条门禁 | 训练答对 44/193；13 条候选。逐条门禁：10 条通过但无新答对，**3 条误伤被单独拦下**（5 → 3 / 5 → 4），没有建议批准的条目 | 30 题开发集太小、个别题对 prompt 变化敏感 → 计划从训练集另留验证集做门禁；两条相反的选表偏好 → 挖掘要处理冲突；反馈表权限 → 读取失败时跳过并告警 |
| 第 4 次 | 挖掘 200 题 + 验证集 200 题（194 题可判分）门禁，冲突处理，读到 1 条用户反馈 | 12 条候选；**academic_terms 补表提示验证集 41 → 42、零误伤，建议批准**（开发集复核 5 → 5）；tip_subject_offered 补表提示 41 → 45、关联规则 41 → 43，净收益为正但有 2–3 题误伤被驳回 | 零误伤对 glm 太严格（dw_4046 在 6 条候选下都翻转）→ 计划先测噪声基线，再改为净收益 + 误伤容忍度 |

## 7. 讲解要点

- "外循环参照企业做法设计成评测驱动 + 人在环路：系统自动从失败中归纳候选知识，每条附证据，逐条在开发集上回归，最后由数据工程师批准才上线，停用即可回滚。"
- "我用训练集的 Gold 模拟企业的已验证查询日志；换到生产环境，把信号源换成用户反馈和人工抽检，结构不变。"
- "迭代本身也在迭代：第 1 次挖不出候选，第 2 次门禁拦下了会误伤的一批，分别让我改了挖掘规则和门禁粒度。这些都是数据告诉我的，不是事先设计好的。"
- "全量统计和错误驱动两层叠加：前者告诉模型'通常怎么用'，后者针对'用了全量知识之后仍然犯的错'。"

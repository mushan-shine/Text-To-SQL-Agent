# ⑥ 评测

> 一句话：**Loop 结束之后**才对照 Gold 判分；除了准确率，还要看**恢复率、误伤率、成本**；三份数据各有用途，互不越界。
> 评测代码是项目里唯一能读 Gold 的地方（除了离线的外循环学习）。

---

## 1. 设计原理与价值

### 1.1 要回答的问题

一个"自我修复"系统至少要回答四个问题，只看最终准确率回答不了：

| 问题 | 指标 |
|---|---|
| 修复把多少错题修对了？ | **恢复率** = 首次错且最终对 / 首次错 |
| 修复把多少对题改错了？ | **误伤率** = 首次对且最终错 / 首次对 |
| 净效果多大？ | **净收益** = 恢复数 − 误伤数 |
| 值不值？ | 平均尝试次数、额外 token、**每净恢复一题的额外 token** |

此外还要知道每个环节的质量：自检的命中 / 误报 / 漏报，诊断的准确率，每个修复技能的效果。

### 1.2 设计原则

| 原则 | 做法 |
|---|---|
| **判分在 Loop 之外** | 判定器只在 `controller.run` 返回之后调用；对错单独存字段，不写回尝试记录 |
| **对错和过程分开存** | 过程进 `traces`，对错进 `evaluation`（[02](02_平台层.md)） |
| **数据三分** | 训练集学习、开发集调参和门禁、评测集只在配置冻结后跑 |
| **上界单独标注** | 用了 Gold 信息的实验（Oracle 自检、干预实验）只作上界参考，不代表系统能力 |
| **标签也要验证** | 失败标注器先对 Gold 自身做自检（零误报），再做人工抽检 |
| **先离线评估，再接入** | 任何新的自检方法先测"抓错率 / 误报率" |

### 1.3 价值

- 让每个结论都有数字：例如"定向修复让 glm 可执行从 4 道提到 9 道"、"LLM 裁判误报 31/33 所以不接入"。
- **误伤率**是自我修正系统最容易忽略的风险，这里把它和恢复率并列。
- 评测集只在配置冻结后使用（决策 D2），避免"在考题上调参"。

## 3. 各模块的设计原理与代码实现

### 3.1 三份数据

| 数据 | 规模 | 来源 | 用途 | 判分方式 |
|---|---|---|---|---|
| **评测集** | 89 PRIMARY（100 题抽样中） | 官方种子 77 抽样 + Phase 0 资格审查 | 配置冻结后跑一次，报告正式成绩 | 冻结的 `benchmark.gold_results`，官方 EX 比较（`evaluate_against_gold`） |
| **开发集** | 30 题 | 评测集以外，种子 20260926 | 所有 prompt / 模型 / 参数迭代；外循环门禁 | MySQL 上实时算出的 Gold 行，跨引擎比较 |
| **训练集** | 约 5,650 道 | 其余全部已解题 | 相似题示例库、数仓使用说明、外循环抽题 | 外循环里用 Gold SQL 在 Databricks 上现场执行 |

**开发集构建**：[devset.py:67](../../evaluation/devset.py#L67) `build_devset`

```python
pool = 评测集以外、few-shot 示例以外的 dw 题，按 random.Random(20260926) 打乱
for e in pool:
    ref  = mysql.execute(e.sql)                        # 官方引擎算 Gold，必须非空
    cand = dbx.execute(apply_rules(e.sql))             # Databricks 上必须能复现
    if cross_engine_match(cand.rows, ref.rows).set_match:
        kept.append({..., "mysql_rows": encode_rows(ref.rows)})   # 无损保存 Decimal 精度
    if len(kept) == 30: break
```

和 Phase 0 的资格标准一样：看了 34 道候选，淘汰 4 道（3 道 Databricks 上无法复现，1 道报错）。`encode_rows`（[devset.py:59](../../evaluation/devset.py#L59)）把 `Decimal` 存成字符串，保留小数位，跨引擎比较需要它。

**为什么要开发集**：Phase 1 的 20 题试点是在评测题上做的，发现 prompt 规则和题干冲突后，如果继续在评测题上改 prompt，就等于在考题上调参。所以决策 D2：之后所有迭代只在开发集上做。

### 3.2 Loop 评测：事后判分

**实现**：[loop_run.py:36](../../evaluation/loop_run.py#L36) `run_arm`

```python
for case in cases:
    res = controller.run(case.agent_view(), verifier_for(case.case_id), on_event=cb)   # Loop 只拿到 AgentTask
    judge   = judges[case.case_id]                                                     # Loop 结束后才取判定器
    correct = [judge(rows)[0] if a["execution_status"] == "SUCCESS" else False
               for a, rows in zip(res.attempts, res.rows)]                              # 每次尝试都判
    rec = {"attempts": res.attempts, "attempt_correct": correct, "final_index": res.final_index,
           "first_correct": correct[0], "final_correct": correct[res.final_index], "tokens": ..., ...}
    on_event(case.case_id, "judged", {...})         # 网页上"Gold 判分"一步来自这里，不来自 Loop
```

每个运行一个目录 `runs/phase6/<run_id>/`：`run_meta.json`（配置和版本号）、`results.jsonl`（逐题）、`summary.json`（指标）。

**指标**：[loop_run.py:78](../../evaluation/loop_run.py#L78) `summarize`

```python
recovered = Σ (not first_correct and final_correct)
harmed    = Σ (first_correct and not final_correct)
recovery_rate = recovered / (n - first)
harm_rate     = harmed / first
net_gain      = recovered - harmed
extra_tokens_per_net_recovery = 第 2 次及以后尝试的 token / net_gain
verifier_confusion（第 1 次尝试）：命中 = 自检不通过且确实错；误报 = 不通过但其实对；
                                  漏报 = 通过但其实错；正确放行 = 通过且对
per_skill：每个技能被用了几次、修完能执行几次、修对几次
```

**自检方式**：`verifier` 可选 self（只看可观察信号，正式结果）或 oracle（拿 gold 判对错，只用来估算修复能力的上界）。两种方式共享第 1 次尝试（相同 prompt 命中缓存），差异只来自自检方式。Oracle 结果一律标"上界"。

### 3.3 基线评测

[baseline.py:52](../../evaluation/baseline.py#L52) `run_case`：检索 → 生成 → 执行 → 判分，一次尝试。多记两个**仅用于评测的诊断字段**：`eval_table_recall`（检索召回了几成 Gold 表）、`eval_all_gold_tables_retrieved`。它们只进 `evaluation.*`，不交给 Agent。

评测集判分：`gold_judge(gold_json)` → `evaluate_against_gold`（[evaluator.py:56](../../benchmark/beaver/evaluator.py#L56)）：生成结果先规范化（和冻结 Gold 的格式一致），再用 BEAVER 官方比较：行集合相同、列顺序有意义、列名忽略。

### 3.4 失败标注器：答错了，错在哪

**原理**：把生成的 SQL 和 Gold SQL 都解析成语法树（别名还原成真实表名），逐项比较表、列、关联等式、常量、运算。**参照 = BEAVER 标注 ∩ Gold SQL 实际用到的**：dw 中 18% 的题，标注列出的表比 Gold SQL 实际用的多，直接用标注会把正确答案判成"少选了表"。

**实现**：[subtasks.py:71](../../benchmark/beaver/subtasks.py#L71) `gold_reference`、[subtasks.py:90](../../benchmark/beaver/subtasks.py#L90) `label_failure`

```python
检查顺序（主因取最上游）：选表 → 列映射 → 关联键 → 领域知识 → 查询拆解 → 执行 → 未知
选表   ：Gold 用的表里有生成 SQL 没用的 → 记录每张缺失表是"检索到但没用"还是"没检索到"
列映射 ：生成 SQL 已用的 Gold 表里，缺少 Gold 用到的列
关联键 ：两张表都用了，但缺少 Gold 的等值关联
领域知识：题干术语对应的 Gold 常量没出现
查询拆解：Gold 的运算类型（分组、窗口、统计、集合运算）缺失
```

**验证**：Gold SQL 对照自身，开发集 30/30、评测样本 100/100 零误报；人工抽检 20 题，严格一致 75%、宽松 90%。

用途：Phase 3 失败分布、诊断准确率的参照、`analyze_run` 错误分析、外循环错题标注。

### 3.5 干预实验：缺信息还是能力不够

[intervention.py:44](../../evaluation/intervention.py#L44) `build_hints`、[intervention.py:75](../../evaluation/intervention.py#L75) `classify`

对每道错题重新生成，每次**只补一类 Gold 提示**（表 / 列 / 关联键 / 领域知识 / 子问题，BEAVER setting=1/2 的做法），另跑一次 5 类全补的上界：

```
只有补 X 能修好       → 因果类型 X
补多种都能单独修好    → MULTIPLE_SUFFICIENT
只有全补才修好        → MULTI_CAUSE
全补也修不好          → UNRESOLVED（超出模型能力）
```

结果决定了项目方向：

| 模型 | 5 类 Gold 提示全补能修好 | 结论 |
|---|---|---|
| glm-4-flash | 0/30 | 瓶颈在模型能力，补信息的 Loop 恢复率会接近 0（决策 D3 / D4：先用它搭工程结构） |
| deepseek-flash | 7/27 | 给对信息能改对，Loop 有发挥空间（修好的 7 题主因都是选表） |

这些 SQL 是在 Gold 提示下生成的，**只发布汇总，不进 `traces`**（[publish.py:157](../../dbx/publish.py#L157)）。

### 3.6 诊断准确率

[diagnosis_eval.py:18](../../evaluation/diagnosis_eval.py#L18) `score`：诊断结果（运行时、无 Gold）对照标注器标签。

- 严格：诊断 = 标签主因；宽松：诊断 ∈ 所有未通过的检查。两个都报，因为主因是按依赖顺序的约定，不是因果证明。
- 评测集 87 个失败：整体严格 40.2% / 宽松 66.7%；规则级宽松 **76.5%**；LLM 级严格 0/19。

### 3.7 自检方法的离线评估

每个候选自检方法都在两类样本上测：

- **抓错**：开发集运行中"能执行但答错"的尝试（30 个，按题目 + SQL 去重）；
- **误报**：开发集 30 道 Gold SQL 及结果、评测集以外的 Gold SQL（静态检查用 5,687 道；数值检查用 MySQL 上执行的 399 道）。

结果和接入决定见 [04](04_内循环Loop.md) 第 3.2 节。这一套评估本身是项目的一个方法论亮点：**先量化，再接入**。

### 3.8 单次运行错误分析

[scripts/analyze_run.py](../../scripts/analyze_run.py)：从 Delta 拉一次运行的 trace 和判分，取每道题的最终答案，用失败标注器和结果级比较（列数、行数、数值）逐题解释错因。它把"deepseek 21 道能执行但错"分成 6 类（[05](05_外循环.md) 第 1.1 节），直接决定了外循环先做什么。

## 4. 数据流转

```
                  ┌── 评测集：benchmark.gold_results（冻结，89 PRIMARY）──┐
Gold 来源 ────────┼── 开发集：runs/phase1/devset.json（MySQL Gold 行）────┼──▶ judges[case_id](rows) → (对错, 原因)
                  └── 训练集：Gold SQL 在 Databricks 现场执行（外循环）───┘
                                                                          │
cases ──▶ controller.run(case.agent_view()) ──▶ LoopResult（attempts, rows）
                                                    │  Loop 结束后
                                                    ▼
                                    attempt_correct = [judge(rows) for each attempt]
                                                    ▼
                  runs/<phase>/<run_id>/results.jsonl + summary.json（恢复率、误伤率、成本、自检混淆……）
                                                    ▼  publish_run
                  traces.execution_traces（过程，无对错）   evaluation.evaluation_results / runs（对错、指标）
                                                    ▼
                  离线分析：label_failure → evaluation.failure_labels → diagnosis_eval / analyze_run → 外循环
```

## 5. 关键结果汇总

| 阶段 | 结果 |
|---|---|
| Phase 1 正式基线（评测集 89，glm） | 首次准确率 2/89，可执行 21/89；报错 68 题中 `UNRESOLVED_COLUMN` 58 |
| Phase 3 失败分布（87 个失败） | 主因：选表 76、列映射 7；缺失的 Gold 表"检索到但没用" 132 次 vs 没检索到 32 次 |
| Phase 4 诊断准确率 | 规则级宽松 76.5%，LLM 级严格 0/19 |
| Phase 6 Loop（开发集，glm） | 可执行 4 → 9；恢复 0（glm 能力上限） |
| 生成端改进（开发集，glm） | 答对 0 → 3（相似题示例）→ 5（+ 使用说明） |
| deepseek + 相似题示例 + Loop | 最终答对 8/30 |

## 6. 讲解要点

- "判分永远在 Loop 结束之后。对错存在 evaluation 里，不在 trace 里，Loop 读不到。"
- "我同时报恢复率和误伤率，因为自我修正最大的风险是把对的改错。"
- "三份数据分工明确：训练集学、开发集调、评测集冻结后才跑。第一次试点发现自己在考题上调参后，立刻建了开发集。"
- "干预实验告诉我 glm 给了全部标准答案提示也修不好，这是换模型的依据；deepseek 能修好 7/27，说明 Loop 有空间。"

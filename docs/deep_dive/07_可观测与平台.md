# ⑦ 可观测与平台

> 一句话：让每一次运行**看得见、查得到、能复现**：本地运行目录 → Delta + MLflow → 网页（提问、审核、Console、运行 Loop）→ 部署成 Databricks App。
> 线上地址：https://self-healing-text2sql-7474651013274104.aws.databricksapps.com（需 Databricks 登录）

## 1. 设计原理与价值

### 1.1 要解决的问题

- Loop 是多步系统，"最终答错"可能错在检索、生成、自检、诊断、修复任何一步。没有逐步记录，就没法调试。
- 实验很多（模型 × 示例方式 × 知识 × 策略 × 自检 × 修复次数），结果必须和配置一一对应，否则对比没有意义。
- 系统要给真实用户用：能提问、能反馈、改动能审核。

### 1.2 设计原则

| 原则 | 做法 |
|---|---|
| **trace 是调试器** | 每次尝试一行，记录看到了什么、做了什么、结果如何；网页时间线逐步展开 |
| **版本号写进元数据** | 模型、厂商、prompt 版本、自检版本、诊断器版本、示例方式、知识开关都记录在 `run_meta.json` |
| **发布幂等** | 同一 run_id 重复发布，先删旧行再写；MLflow 按 run_id 标签复用 |
| **网页和命令行同一条路径** | 网页"运行 Loop"调用的就是评测用的 `run_arm` 和 `LoopController` |
| **自检通过 ≠ 答对** | 网页、报告、Console 分开展示；"自检通过但 Gold 判错"标为漏报 |
| **安全默认** | key 放 secret；BEAVER 数据不入库；评测集在网页上锁定；审核人可以限定 |

### 1.3 价值

- 任何一次运行都能回答"这道题为什么修、修了什么、修完怎样"。
- 线上可演示：选题 → 实时看 Loop 一步步执行 → 自动生成分析报告和图表。
- 产品闭环可演示：用户提问 → 反馈 → 外循环提案 → 审核 → 下一题生效。

### 3.1 运行目录 → Delta + MLflow

**实现**：[publish.py:179](../../dbx/publish.py#L179) `publish_run`

```python
meta, summary, records = load_run(run_dir)             # :24
#   Loop 运行：每题一条记录（含 attempts 列表）→ flatten_loop_records（:35）展平成每次尝试一条，

```

`build_rows` 的分流就是 Gold 隔离的最后一道关：

| 表 | 内容 | 含对错 |
|---|---|---|
| `traces.execution_traces` | 问题、检索表、SQL、执行状态 / 报错 / 结果预览、自检结论 / 信号、诊断、修复、模型、prompt 版本、token、耗时 | ❌ |
| `evaluation.evaluation_results` | 每次尝试是否答对、表召回 | ✅ |
| `evaluation.runs` | 运行汇总、配置 JSON、MLflow run id | ✅ |

干预实验（Gold 提示下生成的 SQL）只发布汇总到 `evaluation.runs`，不进 `traces`（`intervention_run_row`，[:157](../../dbx/publish.py#L157)）。

网页上的运行跑完会自动发布；命令行运行用 `python scripts/publish_run.py runs/phase6/<run_id>`。

### 3.3 后台执行和实时刷新

**原理**：一道题要跑 30–60 秒，Streamlit 页面不能阻塞。做法是**后台线程跑 Loop，事件追加到列表，页面每秒读一次列表重绘**。

**实现**：[runner.py:148](../../app/runner.py#L148) `LiveRun`（运行页）、[runner.py:307](../../app/runner.py#L307) `AskRun`（提问页）

```python
@dataclass
class LiveRun:
    events: list[dict]; status: str = "running"; _lock: threading.Lock
    def push(self, case_id, step, payload):            # Loop 的 on_event 回调
        with self._lock: self.events.append({"t": 秒数, "case_id": ..., "step": ..., **payload})
    def snapshot(self):                                 # 页面每秒调用一次
        with self._lock: return list(self.events)

threading.Thread(target=_execute, args=(live, bundle, connect), daemon=True).start()   # start_run，:289
```

页面端（[run_loop.py](../../app/app_pages/run_loop.py) 末尾）：

```python
st.fragment(live_panel, run_every=1 if running else None)()   # 只有运行中才每秒刷新这一块
# 运行结束后 st.rerun(scope="app") 一次，让表单恢复可用
```

**控制器组装集中在一处**：[runner.py:193](../../app/runner.py#L193) `build_controller`。运行页和提问页都用它，和命令行 `scripts/phase6.py` 的组装方式一致：检索器、生成器（示例 / 使用说明 / 已审核知识）、执行器、诊断器、Policy、修复上下文。

每个运行线程有**自己的数据库连接**（`connect()`），避免多个页面会话共用一个游标。每次点击都有 LLM 调用预算：每题 1 次生成 + 每轮修复约 2 次调用。

### 3.4 时间线组件

[trace_view.py:24](../../app/trace_view.py#L24) `render_case(events, active)`：把一道题的事件渲染成 Streamlit 步骤：

| 步骤 | 展示 |
|---|---|
| 检索 | 候选表和 BM25 分数 |
| 生成 | token、耗时、是否缓存；prompt 构成；相似题示例 id 和补充的表；数仓使用说明 / 审核知识原文；SQL；完整 prompt |
| 执行 | 成功行数或报错类别；耗时；结果前 5 行 |
| 自检 | 通过 / 不通过；触发项（红）和提示项（蓝），带证据 |
| 观察 | Observer 白名单字段、从报错解析出的信号 |
| 诊断 | 失败类型、置信度、原因、来源（规则 / LLM）、修复线索 |
| 路由 | 选中的技能、是否 fallback |
| 修复 | 技能动作、确定性修改、候选列 / 关联键、给 LLM 的指令和 prompt、修复前后 SQL 差异 |
| 最终 / 判分 | 选中的尝试；（运行页）Gold 判分，明确标注"由评测侧在 Loop 结束后给出" |

### 3.5 分析报告

[report.py:159](../../app/report.py#L159) `build_report`：运行结束后**只用事件**生成 Markdown，不调用 LLM：总体结果、逐次尝试的变化、逐题结局、各环节表现（自检命中 / 漏报、诊断分布、技能效果）、时间与成本、自动得出的发现。

图表数据由 `first_final` / `attempt_progress` / `status_grid`（[report.py:106](../../app/report.py#L106) 起）计算，有单元测试；页面只负责画：修复前后柱状图、逐次尝试折线图、逐题 × 逐次状态格子图（★ 标最终答案）。

### 3.6 提问页

[ask.py](../../app/app_pages/ask.py)：

```
输入问题（+ 模型、最大修复次数；高级：相似题示例 / 使用说明 / 已审核知识开关）
  → runner.start_ask(AskRun(...))        后台线程 _ask（runner.py:352）
       build_controller(...) → controller.run(AgentTask(query_id, question, "dw"), SelfVerifier(), on_event)

       experience.save_user_query(...)   问题、最终 SQL、状态、尝试次数、token、耗时、全部尝试 JSON
  → answer_block：自检结论、尝试次数、行数、用时；最终 SQL；结果表
  → 执行过程（时间线，运行中自动展开）
  → feedback_block：👍 / 👎；👎 时选原因、可填正确的 SQL、备注
       runner.submit_feedback（runner.py:412）：修正 SQL 先只读执行（得到 SUCCESS / ERROR）→ experience.save_feedback
```

- 用户身份：Databricks Apps 通过请求头 `X-Forwarded-Email` 传入，本地为 `local-user`（`current_user`，[ask.py:31](../../app/app_pages/ask.py#L31)）。
- 提问页**只能用 SelfVerifier**：用户问题没有 Gold。
- 反馈是**弱标签**，不直接变成知识，只作为外循环的候选来源（[05](05_外循环.md)）。

### 3.7 审核页

[review.py](../../app/app_pages/review.py)，四个标签页：

| 标签页 | 内容 | 操作 |
|---|---|---|
| 待审核 | 按批次：本批训练集错因分布、合用复核结果；每条提案：内容（写进 prompt 的原文）、证据（错题 id、例题、错误 SQL）、**这条自己的开发集回归**、建议（✅ / ➖ / ⛔） | 批准上线、驳回，可填审核意见 |
| 已生效知识 | active 条目，批准人、时间 | 停用（回滚） |
| 用户反馈 | 每个问题最新一条反馈、修正 SQL 是否能执行 | 只读 |

- 数据读取带 60 秒缓存，审核操作后主动清缓存刷新。
- 兼容旧格式：整批回归的旧提案（outer-v1 早期）按批次显示一个回归结果。

```
     └─ 👍/👎 + 修正 SQL（先执行校验）──▶ experience.feedback ──▶ 外循环（离线）
                                                                    │

```

## 5. 运维要点

- Free Edition 下 App 和 Warehouse 会被自动停止，页面打不开时分别启动（命令见 [02](02_平台层.md) 第 5 节）。
- 更新代码后：`build_app_bundle.py`（数据变了才需要）→ `deploy_app.py --skip-secrets`。
- App 的服务主体在线上**首次**写某张表时会成为该表所有者，本机账号可能读不到（例如 `experience.feedback`）；外循环读取失败会跳过反馈挖掘并告警。

## 6. 讲解要点

- "每次尝试一行 trace，网页时间线逐步展开：检索了什么、prompt 里有什么、自检发现什么、诊断成什么、技能做了哪些确定性修改、给 LLM 的指令是什么。"
- "网页运行和命令行实验走同一条代码路径，结果可以互相对照；版本号全部写进元数据。"
- "产品闭环也在网页上：用户提问和反馈、数据工程师审核外循环提案、批准后下一题生效、随时停用回滚。"
- "部署时 key 放 secret、数据集不入库、评测集默认锁定、服务主体只拿项目 catalog 的权限。"

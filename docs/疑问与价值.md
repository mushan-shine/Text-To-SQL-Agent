## 疑问 1：企业真实场景是不是没办法直接用通用模型，一般都要基于模型做微调？

### 结论

不是。企业真实场景的**主流做法是通用大模型 + 上下文工程**，微调只在特定条件下才用。

### 主流做法：通用模型 + 企业上下文

| 产品 | 模型 | 企业知识放在哪里 |
|---|---|---|
| Databricks AI/BI Genie | 通用大模型 | 空间说明、示例 SQL、可信资产、表和列的注释 |
| Snowflake Cortex Analyst | 通用大模型 | 语义模型文件（指标、维度、同义词）、已验证查询库 |
| Uber QueryGPT、Pinterest、LinkedIn 的内部工具（公开工程博客） | 通用大模型 | 业务领域划分、历史查询检索、元数据和知识图谱 |

共同点：企业知识放在**上下文**里，而不是模型参数里。

### 为什么大多数企业不先做微调

1. **数仓一直在变**：表、字段、口径会增删修改。知识放在上下文里，改一份文档立刻生效；放进参数里，每次变化都要重新训练，否则模型会记着过时的结构。
2. **需要大量标注数据**：微调需要成千上万条"问题 → 正确 SQL"，大多数企业一开始没有。
3. **可解释、可审核**：上下文里的知识能查、能改、能追溯出处；放进参数里，说不清模型为什么选这张表。
4. **成本和追新**：通用模型几个月就更新一代，能力大幅提升；微调模型被固定在当时的基座上，换基座要重新训练。
5. **效果不一定更好**：强通用模型加上好的上下文，往往优于弱模型微调，而且维护成本低得多。

### 什么情况下会做微调

| 场景 | 原因 |
|---|---|
| 数据不能出内网 / 必须私有化部署 | 只能用开源小模型，小模型不微调通常能力不够 |
| 调用量极大 | 微调后的小模型推理便宜、速度快，可以替代昂贵的大模型 |
| 特殊的 SQL 方言或内部查询语言 | 通用模型很少见过，靠提示效果差 |
| 已积累大量高质量的已验证查询 | 有了足够的训练数据，微调才划算 |
| 输出格式和风格要高度统一 | 如固定的 CTE 写法、命名规范 |

即使做了微调，**通常也还要配合检索和上下文**：微调教"怎么写这类 SQL"，检索提供"现在有哪些表、口径是什么"，两者不互相替代。

常见的演进路线：
1. 先用通用模型加上下文快速上线；
2. 通过用户反馈和人工审核积累已验证查询；
3. 调用量上来后，再用这些数据微调小模型来降成本。

### 对照本项目

- **本项目走的就是主流路线**：通用模型（glm-4-flash / deepseek-flash），加上外循环从已解题归纳的知识（相似题示例、数仓使用说明）。这相当于自动化了"企业维护语义层和已验证查询库"的那部分工作。
- **数据说明模型能力很重要**：同样的系统，开发集上 glm 答对 5 题，DeepSeek 答对 8 题；干预实验里，给了全部 Gold 提示，glm 修好 0/30，DeepSeek 修好 7/27。上下文再好，模型能力不够也用不上。
- **项目也具备微调的条件**：训练集有约 5,500 道"问题 → Gold SQL"。外循环归纳出的知识，本质上就是微调会学到的东西，只是放在上下文里，而不是放进参数里。

### 面试回答参考

> "我的项目用的是通用模型加上下文工程，这也是 Genie、Cortex Analyst 这类企业产品的主流做法。原因是数仓结构经常变化，上下文里的知识改完立刻生效、可以审核；放进参数里就要反复训练。我的外循环从 5,500 道已解题里统计用表和关联约定，相当于'不训练的微调'。什么时候考虑真正微调：数据不能出内网只能用开源小模型、调用量大需要降成本，或者已经积累了足够多的已验证查询。即使微调了，我也会保留检索和上下文，因为微调学的是写法，检索提供的是当前的数仓知识。"

## 疑问 2：企业在构建系统前，也会有训练集、开发集、评测集吗？

### 结论

会有，但**形式和叫法不一样**，也不是先有一个现成的公开数据集。企业一般是在建系统的过程中，自己把这三类数据逐步攒出来。

### 企业里对应的三样东西

| 本项目 | 企业里通常叫 | 从哪来 | 用途 |
|---|---|---|---|
| **训练集**（约 5,500 道已解题） | **知识来源**：历史查询日志、已验证查询库、语义层 / 指标定义 | BI 工具和数仓里历史执行过的 SQL、报表背后的 SQL、分析师写好的常用查询 | 作为检索示例和上下文。多数情况下**不拿来训练模型**，除非要微调 |
| **开发集**（30 题） | **调试集 / 迭代集** | 业务方常问的问题，数据分析师给出正确 SQL | 改 prompt、说明、示例时快速看效果 |
| **评测集**（89 题） | **基准问题集 / Golden Set / 回归测试集** | 数据负责人挑选并审核的问题和标准答案，覆盖核心指标和易错场景 | 每次上线前必须跑、准确率不能下降，类似软件的回归测试 |

产品中的例子：
- Databricks Genie：有"基准问题"功能，数据负责人录入问题和标准 SQL，改配置前后对比准确率；
- Snowflake Cortex Analyst："已验证查询库"用来提供示例；
- 开源 Vanna：用户确认正确的"问题-SQL"对会加入训练库，用于检索。

### 怎么攒这些数据

1. **从历史 SQL 反推问题**：拿现有报表和查询日志里的 SQL，由人或 LLM 写出对应的自然语言问题，再人工审核。BEAVER 大致也是这样构建的，所以它的题干和 SQL 会有不一致。
2. **分析师标注**：选出业务上最常问、最重要的几十到几百个问题，由熟悉数据的人写出标准答案。
3. **上线后从反馈中积累**：用户采纳的答案经审核进入已验证查询库；用户说"不对"的问题，修好后加进回归测试集。

规模通常不大：评测集起步几十到一两百题即可，重点是**覆盖核心指标和易错场景**、答案可靠。

### 和本项目相比

**企业的做法没那么严格的地方**：
- 开发集和评测集经常不分开，只有一套"基准问题"，边调边测。风险是**在考题上调参**：基准集准确率很好，遇到新问题就不行。
- 已验证查询库和评测集容易**混在一起**：评测题的标准答案如果也在示例库里，检索会直接把答案带出来，准确率虚高。这就是本项目给示例库和知识库做泄漏检查的原因。

**企业的做法更强的地方**：
- 有**线上指标**：采纳率、点赞 / 点踩、追问率、人工抽检，这是离线评测替代不了的。
- 评测集会**持续更新**：随着数仓变化、新问题出现，不断加入新题。

### 面试回答参考

> "企业做 Text-to-SQL 通常只有一套'基准问题'，调参和评测用同一批题，容易虚高；已验证查询库里如果混进了评测题，检索还会直接把答案带出来。我的项目把数据分成三份：训练集只用来学知识，开发集只用来衡量改动，评测集配置冻结后只跑一次，示例库和知识库都做过泄漏检查。落到企业里，就是把'基准问题集'拆成迭代集和冻结的回归集，再加上线上反馈，形成持续更新的闭环。"

## 疑问 3：为什么用 BM25 检索 20 张候选表？为什么是 20 张？会不会有题需要超过 20 张表？

### 结论

- 选 BM25 是为了**简单、确定、可解释**；
- 20 是**用数据调出来的拐点**；
- BEAVER 里**没有**需要超过 20 张表的题（最多 8 张）。真正的风险是 20 张里漏掉了该用的表，项目对此有补救，但并不完美。

### 为什么选 BM25

BM25 是按"关键词重合度"打分的经典检索算法。这里把每张表当成一篇文档（表名、列名、样例值），把问题当成查询。

| 考虑 | BM25 | 向量检索 / LLM 选表 |
|---|---|---|
| 匹配方式 | 数仓的表名、列名本身就是英文业务词（`NUM_ENROLLED_STUDENTS`、`DEPARTMENT_NAME`），和题干用词重合度高，关键词匹配天然有效 | 能理解同义词，但对这种命名规整的 schema，优势不明显 |
| 确定性 | 同样的问题永远得到同样的结果，实验可复现 | 向量模型有版本变化；LLM 选表还有随机性 |
| 成本 | 本地计算，不调用 API、不花钱 | 需要向量服务或额外的 LLM 调用 |
| 可解释 | 能看到每张表的分数和命中了哪些词（运行页的检索步骤展示 BM25 分数） | 很难解释为什么选了这张表 |
| 定位 | 业界常用的强基线，先把简单方法做到位，再用数据证明需不需要换 | 可作为后续改进方向 |

实现细节（[agent/retriever.py](../agent/retriever.py)）：
- 表名、列名、样例值的权重为 3 / 2 / 1，因为问题里提到的更多是概念（表和列），而不是具体数据；
- 分数相同时按表名排序，保证结果确定。

### 为什么是 20 张

这个数是在**评测集以外**的题上调出来的，记录在 [config/phase1.yaml](../config/phase1.yaml) 的注释里。在训练集随机抽 300 题复测的结果：

| k | 平均召回率 | 该用的表全部选中的题 |
|---|---|---|
| 10 | 0.757 | 38% |
| 15 | 0.858 | 58% |
| **20** | **0.914** | **71%** |
| 25 | 0.948 | 81% |
| 30 | 0.964 | 87% |
| 40 | 0.986 | 94% |

选 20 是在两方面之间找平衡：
- **召回**：从 10 到 20，平均召回率提高 16 个百分点；从 20 往上，每多 5 张只提高 2–3 个百分点，收益开始变小。
- **prompt 长度和干扰**：20 张表的 schema 约 3.3 万字符（约 1.3 万 token），全部 97 张约 9.5 万字符。表越多，prompt 越长、成本越高，而且**相似的表越多，模型越容易选错**，而错误分析已经证明选错表正是主要错因。

### 会不会有题需要超过 20 张表

在 BEAVER 里不会。训练集 5,687 道题中，每道题的 Gold SQL 用到的表数：

| 用到的表数 | 占比 |
|---|---|
| 2–5 张 | 94% |
| 6 张 | 4.7% |
| 7–8 张 | 0.5% |
| 最多 | **8 张** |

所以"20 张不够装"并不是问题。**真正的问题是 20 张里没选中该用的那几张**：k=20 时，只有 71% 的题把该用的表全部选中了。

### 漏选时的补救措施

| 措施 | 位置 | 作用 |
|---|---|---|
| 相似题示例补充表 | [agent/generator.py](../agent/generator.py) | 相似的已解题用到、但检索没选出的表，最多补 6 张进 schema |
| 修复阶段补表 | 诊断 + RetrieveAgain | 报错"找不到某列"时，诊断在**全部 97 张表**里查这个列属于哪张表，即使那张表没被检索到（`not_retrieved`），RetrieveAgain 也会把它加进来 |
| 数仓使用说明 | [agent/knowledge.py](../agent/knowledge.py) | 提示模型同类问题通常用哪些表 |

**局限**：如果漏掉的表没有导致报错（SQL 用别的表也能跑通），修复阶段就发现不了，只能靠生成阶段的补救。

**检索目前不是主要瓶颈**：DeepSeek 那次运行中，Gold 用到但生成 SQL 没用的表共 41 次，34 次（83%）其实已经在 20 张候选表里，是模型在里面选错了。所以现阶段加大 k 或换检索算法收益有限，重点仍然是帮模型在候选表中选对。

### 面试回答参考

> "我用 BM25 做表检索，因为这个数仓的表名、列名就是业务词，关键词匹配有效，而且确定、免费、可解释，是个强基线。k=20 是在评测集以外的题上调出来的拐点：召回率 0.91，再往上每加 5 张只提升 2–3 个点，但 prompt 更长、相似表的干扰更多。BEAVER 的题最多用 8 张表，所以 20 张容量足够，真正的风险是漏选。对此我有三层补救：相似题示例补表、修复时在全部表里定位缺失的列、外循环的使用说明。错误分析也显示，漏用的表 83% 其实已经检索到了，所以瓶颈在'选对'而不在'检索到'。"

# 代码理解类疑问

> 以下是阅读生成端代码时的疑问，按"单个函数 → 算法原理 → 模块之间的区别"组织。

## 疑问 4：`render_schema` 函数的作用是什么？

### 结论

把选中表的结构转成一段文本放进 prompt，让模型知道能用哪些表、哪些列、列里大概存了什么值。**它是模型"看到"数仓的唯一窗口。**

### 代码

[agent/generator.py](../agent/generator.py) `render_schema`

```python
def render_schema(catalog, tables):
    blocks = []
    for t in tables:                                   # 只渲染传入的这几张表，不是全部 97 张
        tb = catalog.tables[t]
        lines = [f"TABLE {catalog.db}.{tb.name}"]      # 表名，带库名前缀
        for c in tb.columns:
            ex = f"  -- e.g. {', '.join(c.examples)}" if c.examples else ""   # 样例值
            lines.append(f"  {c.name} {c.type}{ex}")   # 列名 + 类型 + 样例值
        blocks.append("\n".join(lines))
    return "\n\n".join(blocks)
```

输出示例：

```
TABLE dw.sis_department
  DEPARTMENT_CODE STRING  -- e.g. IDS, ESD, PXL
  SCHOOL_NAME STRING  -- e.g. MIT, academic, Engineering, Hum, Arts & Social Sciences
  IS_DEGREE_GRANTING STRING  -- e.g. Y, N
```

| 信息 | 作用 |
|---|---|
| 列名 | 把题干里的概念对应到列，比如 "department name" 对应 `DEPARTMENT_NAME` |
| 类型 | 决定条件怎么写，比如 STRING 类型的年份要写 `'2022'` |
| 样例值（每列最多 3 个） | 让模型知道值的实际写法（`Y` / `N` 而不是 `true`），减少过滤值写错。样例值来自 BEAVER 官方元数据，不是 Gold（见疑问 11） |

### 调用方

同一个函数被 4 处共用，保证每个环节看到的 schema 格式一致：生成 SQL、修复技能（`llm_repair`）、通用重试（对照组）、LLM 裁判。

### 设计要点

- **只渲染选中的表**：20 张约 3.3 万字符，全部 97 张约 9.5 万字符，只放相关的表，省 token 也减少干扰。
- **确定性**：表和列的顺序固定，同样的输入永远得到同样的文本，prompt 缓存和实验复现都依赖这一点。
- **缺少业务说明**：BEAVER 只有列名、类型和样例值，没有列注释，这是模型容易在相似表之间选错的原因之一。外循环的"数仓使用说明"就是在补这块信息。

## 疑问 5：`r = self.client.complete(prompt, system=SYSTEM)` 这句话的作用是什么？

### 结论

把拼好的 prompt 发给大模型，拿回回答，这是生成步骤里唯一一次调用 LLM 的地方。背后的两层设计保证这次调用**可复现、成本可控、可切换模型、有容错**。

### 三个部分

| 部分 | 是什么 |
|---|---|
| `prompt` | `build_prompt` 拼好的用户消息：规则 + schema + 示例 + 使用说明 + 问题 |
| `SYSTEM` | 系统消息，设定模型身份："You are an expert data analyst who writes Databricks SQL (Spark SQL dialect) for an enterprise data warehouse." |
| `r` | `LlmResponse`：回答原文 `text`、`model`、输入 / 输出 token、耗时、`finish_reason`、`cached`（是否来自缓存） |

下一行 `extract_sql(r.text)` 从回答的 ```` ```sql ```` 代码块中抽出 SQL。

### `self.client` 实际是两层

```python
inner = make_client(...)                          # 第 2 层：真正发 HTTP 请求（智谱或 DeepSeek）
client = CachingChatClient(inner, cache_path)     # 第 1 层：缓存
```

**第 1 层：缓存**（[agent/llm.py](../agent/llm.py) `CachingChatClient.complete`）：用（模型、参数、system、prompt）的 SHA-256 做键；命中就直接返回缓存的回答（不发请求、不花钱）；没命中才往下调用，并写入缓存文件。

**第 2 层：调用模型**（`OpenAICompatibleChatClient.complete`）：
1. 预算检查（`UsageMeter`，超过调用次数或 token 上限直接报错）；
2. 组装成 OpenAI 格式的 system + user 两条消息；
3. 加上解码参数：智谱 `do_sample: False`（贪心解码），DeepSeek `temperature: 0` 并关闭思考模式；
4. POST 到 `{base_url}/chat/completions`（两家都兼容这个接口）；
5. 遇到 408 / 429 / 5xx 等错误，指数退避后重试，最多 5 次；
6. 解析回答和 token 用量，记账。

### 为什么这样设计

| 设计 | 解决什么问题 |
|---|---|
| 缓存 + 贪心解码 | 可复现、对比公平：两个实验组的第 1 次生成逐字相同，组间差别只来自修复策略；重跑不花钱 |
| 统一接口 | 生成、诊断、修复、LLM 裁判都用同一个方法，换模型只改配置 |
| 预算上限 | 防止循环或批量运行失控 |
| 自动重试 | 网络抖动、限流时不至于整批失败 |
| 返回 token 和耗时 | 统计每题成本、每修好一题多花多少 token |

## 疑问 6：BM25 是什么？项目里怎么实现的？

### 结论

BM25 是经典的**关键词检索打分算法**（搜索引擎如 Elasticsearch 默认用它）。项目里用它在 97 张表中找出和问题最相关的 20 张，也用它在已解题中找相似题。

### 核心思想

| 因素 | 含义 | 直觉 |
|---|---|---|
| 词频 TF | 这个词在文档里出现几次 | 越多越相关，但有上限（出现 15 次不代表比 5 次相关 3 倍） |
| 逆文档频率 IDF | 这个词出现在多少篇文档里 | 越稀有越有区分度，见疑问 8 |
| 长度归一化 | 文档比平均长多少 | 列多的大表天然词多，要适当扣分 |

### 公式

```
score(Q, D) = Σ  IDF(w) × TF(w, D) × (k1 + 1)
             w∈Q  ───────────────────────────────────────────
                   TF(w, D) + k1 × (1 − b + b × |D| / avgdl)
```

k1 = 1.2（词频饱和程度），b = 0.75（长度归一化强度），都是常用默认值。

### 项目里的实现（[agent/retriever.py](../agent/retriever.py)）

1. **每张表变成一篇文档**：表名重复 3 次、列名重复 2 次、样例值 1 次（通过重复实现权重；问题里提到的多是概念，所以名字比样例值重要）。
2. **分词**：转小写、拆下划线（`NUM_ENROLLED_STUDENTS` → num / enrolled / students）、去停用词（the、for、each、per、average、number、total…）、简单去复数。
3. **预计算**：每张表的词频、长度，每个词的 IDF。
4. **打分排序**：逐表打分，分数相同按表名排序（保证确定），取前 k 张。

### 真实例子

问题："For each department, give the department name and the average number of enrolled students per subject offered by that department"

| 排名 | 表 | 分数 |
|---|---|---|
| 1 | tip_subject_offered | 13.96 |
| 2 | library_subject_offered | 13.52 |
| 3 | subject_offered_summary | 12.55 |
| 4 | subject_offered | 11.90 |

第 1 名的得分来源：`enrolled`（IDF 3.08，出现 2 次）、`offered`（2.33，5 次）、`student`（1.56，3 次）、`subject`（1.52，15 次，有饱和上限）、`name`（0.47，6 次）、`department`（1.35，**0 次**）。

### 暴露的问题

1. **前 4 名都是相似表、分数非常接近**：BM25 能找到它们，但分不清该用哪张，这就是"选错表"的根源。
2. **字面对不上就会漏**：`department` 在这张表里是 0 次，因为列名写成缩写 `OFFER_DEPT_CODE`。BM25 不懂同义词和缩写。
3. **停用词的取舍**：average、number 被去掉，丢掉一点"要做统计"的信息，但选表用不上。

### 可能的改进

同义词和缩写表（dept ↔ department）、向量检索或混合检索、按已解题统计"问题 → 表"（外循环已在做）、LLM 在候选表中再筛一轮。目前召回率已有 0.91，改进重点放在"选对"。

## 疑问 7：`agent/retriever.py` 和 `agent/examples.py` 有什么区别？`examples.py` 怎么实现、找几条相似题？

### 区别

两者都用 BM25，但检索对象、结果和用途都不同：

| | `retriever.py` | `examples.py` |
|---|---|---|
| 检索什么 | 表 | 已解题（问题 + 标准 SQL） |
| "文档"是什么 | 表名 + 列名 + 样例值 | 已解题的问题文本 |
| 库有多大 | 97 张表 | 5,508 道题（训练集，排除评测集和开发集） |
| 返回什么 | 20 张表名 | 4 道题（问题 + SQL）+ 它们用到的表 |
| 在 prompt 里变成 | `Schema:` 部分 | `Examples:` 部分，用到的表还会补进 schema |
| 回答的问题 | 哪些表可能和这道题有关？ | 以前类似的题，是用哪些表、怎么写的？ |
| 是否一直启用 | 一直启用 | 只在 `--few-shot dynamic` 时启用 |

比喻：retriever 像给新同事一份**数据字典**；examples 像给他看**以前同事写过的类似查询**。

### 为什么两个都需要

漏用的表 83% 其实已经在 retriever 选出的 20 张里：**retriever 负责"找到"已经不错，问题在"选对"**。examples 用已解题示范"这类问题实际用哪张表"，glm 在开发集上答对 0 → 3、能执行 4 → 16。

### `examples.py` 的实现

也是 BM25，自己实现，不调用模型。

**建库**（`ExampleIndex.build`，启动时一次）：
1. 排除评测集、开发集和没有 SQL 的题；
2. 用 Phase 0 的适配规则把 MySQL 写法转成 Databricks 写法；
3. SQL 超过 2,500 字符的不要（避免撑爆 prompt）；
4. 不能被解析为 Databricks SQL 的不要；
5. 记下每条 SQL 用了哪些表。

最后 5,508 道可用，对问题文本分词并预算 BM25 统计量。

**检索**（`top(question, k)`）：新问题分词 → 与所有已解题的问题比 BM25 分数 → 分数相同按题目 id 排序 → 取前 k 道。

**使用**（`FewShotGenerator.generate`）：k 道题作为示例放进 prompt；示例用到、但 retriever 没选出的表，最多补 6 张进 schema。

### 找几条

**4 条**（`config/phase1.yaml` 的 `few_shot.dynamic_k`）。

| 考虑 | 说明 |
|---|---|
| 覆盖 | 相似的前 5 道题用到的表，平均覆盖开发集 Gold 用表的 88.5% |
| prompt 长度 | 每条示例带完整 SQL，4 条让每题平均多约 1,500 token（1.38 万 → 1.53 万） |
| 干扰 | 示例越多，排在后面的越不相似，可能把模型带偏 |

**需要说明**：4 是经验值，**没有像 k=20 那样做过系统调参**。可以在开发集上比较 k = 2 / 4 / 6 / 8 的准确率和成本（用 glm 免费）。

### 防泄漏

示例库排除评测集和开发集；检查过开发集 30 题检索到的示例里没有相同题干或相同 SQL；有单元测试覆盖。

## 疑问 8：IDF 是什么？

### 结论

IDF（Inverse Document Frequency，逆文档频率）衡量一个词**有多稀有、多有区分度**：出现在越多文档里的词，对找出相关文档的帮助越小。

### 公式

```
IDF(w) = ln( 1 + (N − n(w) + 0.5) / (n(w) + 0.5) )
```

N 是文档总数（表检索是 97 张表，相似题检索是 5,508 道题），n(w) 是包含词 w 的文档数。n(w) 越小 IDF 越高；`1 +` 保证不为负，`+0.5` 是平滑。

### 真实数据（97 张表）

| 词 | IDF | 含义 |
|---|---|---|
| enrolled | 3.08 | 很少表有，区分度最高 |
| offered | 2.33 | 较少 |
| student | 1.56 | 中等 |
| department | 1.35 | 较常见 |
| name | 0.47 | 几乎到处都有，区分度最低 |

问题里一个 "enrolled" 的作用，大约顶 6–7 个 "name"。

### 在项目里的三处

- **表检索**（retriever）和**相似题检索**（examples）：BM25 的一部分，得分 = IDF × 词频部分，命中稀有词的文档排在前面；
- **数仓使用说明**（knowledge `table_scores`）：简化版 `ln(N / n(w))`，给问题里的词加权；出现在超过一半题目里的词直接跳过。

### 和停用词的关系

停用词可以理解为"手工指定 IDF 为 0 的词"，直接去掉；IDF 则按数据自动给每个词算重要性。两者配合：停用词去掉最明显的噪声，IDF 处理剩下的词。

## 疑问 9：`agent/knowledge.py` 里各函数的作用是什么？

### 结论

`knowledge.py` 是**外循环的第一份知识资产**：离线从 5,656 道已解题中统计数仓的使用习惯，运行时为每道题挑出相关的几条，作为"数仓使用说明"放进 prompt。

### 函数一览

| 函数 | 何时用 | 作用 |
|---|---|---|
| `_scope_joins(sql, tables)` | 离线 | 解析一条 SQL，按作用域还原别名，找出用了哪些表、有哪些关联（哪两列相等、INNER 还是 LEFT） |
| `WarehouseKnowledge.build(...)` | 离线 | 遍历训练集（排除评测集和开发集），统计三类知识 |
| `to_json` / `from_json` | 离线 → 运行时 | 存成 `runs/knowledge/kb.json`，运行时读回 |
| `table_scores(question)` | 运行时 | 按问题里的词（IDF 加权），估计这类题通常用哪些表 |
| `notes_for(question, schema_tables)` | 运行时 | 只在 schema 已有的表中挑选，生成本题的说明文本（最多 6 张表、8 条关联） |
| `load_knowledge(path)` | 运行时 | 读取知识文件 |
| `knowledge_for(cfg, root)` | 装配时 | 按 `knowledge.mode` 决定是否启用；启用但文件不存在就报错 |

### 统计的三类知识

| 知识 | 怎么统计 | 对应的错误类型 |
|---|---|---|
| 概念 → 表 | 每个题干词（出现 ≥ 5 次）→ 含这个词的已解题用了哪些表 | 选错表（38%） |
| 相似表组 | 列名集合 Jaccard 相似度 ≥ 0.5 且至少 4 个同名列，归为一组；共 4 组 | 选错表 |
| 关联约定 | 每对表的常用关联键和 INNER / LEFT 比例；共 134 对 | 关联方式错误（19%） |

### 输出示例

```
Warehouse usage notes (counted from 5656 solved questions of this warehouse; conventions, not rules):
- Tables that solved questions with similar wording use most (strongest first):
  sis_department (100%), course_catalog_subject_offered (54%), tip_subject_offered (54%), ...
- Look-alike tables (similar columns) - for this kind of question solved queries used:
  tip_subject_offered 74%, library_subject_offered 26%
- Join sis_department - tip_subject_offered: usually sis_department.DEPARTMENT_CODE =
  tip_subject_offered.OFFER_DEPT_CODE (899/900 of 750 queries), INNER JOIN (98%)
```

写成"约定，不是规则"，让模型把它当作参考。

### 调用链

```
离线：scripts/build_knowledge.py → WarehouseKnowledge.build → kb.json
运行：phase1.py / phase6.py / app/runner.py → knowledge_for(cfg) → FewShotGenerator(knowledge=kb)
      → generate() 中 kb.notes_for(question, tables) → build_prompt(..., notes)
```

### 设计要点

- **只用训练集**：学到的是通用规律，不是某道题的答案；
- **不调用 LLM**：纯统计，1–2 分钟建完，确定、可复现、可审核，每条说明都附带次数；
- **按题挑选**：每题只放 7–13 行，prompt 只增加约 3%；
- **效果**：glm 开发集答对 3 → 5（相比只用相似题示例），新答对的两题都属于"选错表"。

## 疑问 10：`knowledge.py` 和 `retriever.py` 有什么区别？

### 结论

两者都会根据问题"找出相关的表"，但依据完全不同：

- retriever 看**表长什么样**：问题的词匹配表名、列名、样例值；
- knowledge 看**以前的题实际用了什么**：问题的词查已解题的统计结果。

### 对比

| | `retriever.py` | `knowledge.py` |
|---|---|---|
| 依据 | 表结构 | 5,656 道已解题的 Gold SQL 实际用表 |
| 回答的问题 | 哪些表**含有**问题里的词？ | 类似用词的题以前**实际用了**哪些表、怎么关联？ |
| 是否用到 Gold | 不用 | 离线统计用训练集 Gold；运行时只读统计结果 |
| 输出 | 20 张候选表 | 一段 7–13 行的说明文字 |
| 在 prompt 里的作用 | 决定 schema 里**放哪些表** | 在已放入的表中**提示优先用哪张、怎么关联** |
| 能否区分相似表 | 不能（列名几乎一样，分数也几乎一样） | 能（统计出实际使用比例） |
| 能否给出关联方式 | 不能 | 能（常用关联键、INNER / LEFT 比例） |

### 同一道题看区别

- **retriever**：tip_subject_offered 13.96、library_subject_offered 13.52、subject_offered_summary 12.55、subject_offered 11.90，只能说"这几张都相关"；
- **knowledge**：类似的题 74% 用 tip_subject_offered；它和 sis_department 通常以 `DEPARTMENT_CODE = OFFER_DEPT_CODE`、INNER JOIN 关联。

### 先后关系，不是二选一

```
问题 → retriever 选 20 张表 → schema（有哪些材料）
     →（examples 补进相似题用到的表）
     → knowledge 只在 schema 已有的表中给出使用说明（习惯怎么用）
     → prompt
```

`notes_for` 只提 schema 里已有的表，所以 knowledge **不增加新表**，只帮模型在已有的表中**选对**。

### 三个模块的分工

| 模块 | 提供什么 | 形式 | 比喻 |
|---|---|---|---|
| retriever | 有哪些表可以用 | 表结构 | 数据字典 |
| examples | 类似的题以前是怎么写的 | 几道具体例题 | 同事写过的查询 |
| knowledge | 整体的用表和关联习惯 | 统计出的规律 | 老同事的经验 |

## 疑问 11：`runs/phase1/schema_dw.json` 基于什么产生、有什么作用？每轮循环会修改吗？可以看作 context 吗？

### 结论

- **来源**：Databricks 上复制后的真实表结构 + BEAVER 官方元数据里的样例值，不含任何 Gold 信息；
- **作用**：它是 **Agent 眼中的数仓**，检索、渲染 schema、诊断、修复、自检、外循环都从这里读取结构；
- **是否修改**：**只读**，只在第一次运行时生成一次，内循环和外循环都不修改；
- **是否是 context**：是，而且是最基础的一层，但它是**静态的 context 源**，每道题只取检索出的子集进入 prompt。

### 基于什么产生

生成代码：[agent/retriever.py](../agent/retriever.py) `SchemaCatalog.from_databricks` → `build`。

| 内容 | 来源 | 说明 |
|---|---|---|
| 表名、列名、列类型 | **Databricks 的 `information_schema.columns`**（复制到 `dw` 后的真实表结构） | 用 Databricks 类型（STRING、BIGINT…），而不是 BEAVER 元数据里的原始 Oracle 类型（VARCHAR2），因为 SQL 在 Databricks 上执行；去掉排序规则后缀 `COLLATE UTF8_LCASE` |
| 样例值（每列最多 3 个，每个最长 40 字符） | **BEAVER 官方 `beaver-table` 元数据**的 `example_columns` 字段（Phase 0 导入的 `benchmark.tables_meta`） | 相当于 BEAVER setting=0 允许 Agent 看到的 schema 信息 |

```python
rows = runner.run("SELECT table_name, column_name, full_data_type "
                  "FROM <catalog>.information_schema.columns WHERE table_schema = 'dw' ...")
cols = [(表, 列, 去掉 COLLATE 的类型) for ...]
return cls.build(db, cols, tables_meta)          # 合并样例值
```

**不包含 Gold**：没有标注的用表、列映射、关联键，也不包含任何题目。

规模：**97 张表、1,530 列**（1,331 列带样例值），约 100KB；格式为 `{"db": "dw", "tables": {表名: [[列名, 类型, [样例值…]], …]}}`。

> 更正：之前的回答（疑问 4）说"样例值是从 Databricks 表里取的"，不准确。样例值来自 BEAVER 官方元数据，类型来自 Databricks。

### 作用

Agent 对数仓的全部结构认知都来自这个文件，Agent 不会直接去查数据库的表结构。

| 使用方 | 用它做什么 |
|---|---|
| BM25 表检索（retriever） | 每张表的文档由它的表名、列名、样例值组成 |
| `render_schema` | 选中的表渲染成 prompt 的 `Schema:` 部分 |
| 诊断（diagnose） | 报错"找不到某列"时，查这个列实际属于哪张表（`column_owners`） |
| 修复技能 | SchemaSearch 修正别名、找相近列名；RetrieveAgain 和 FindJoinPath 推断关联键（`join_graph`） |
| 自检和验证器 | 解析 SQL 时判断列属于哪张表 |
| 外循环 | `build_knowledge` 识别相似表组；错误分析和失败标注还原别名 |
| 网页平台 | 打包进 `app/bundle/schema_dw.json` |

### 每轮循环会修改吗？怎么修改？

**不会，它是只读的。**

- 只在第一次运行时生成（[scripts/phase1.py](../scripts/phase1.py) `load_catalog`）：文件存在就直接读取，不存在才从 Databricks 查询并保存；
- 其他脚本和平台都只用 `from_json` 读取。

**为什么设计成不变**：
- **可复现**：schema 不变，`render_schema` 输出就不变，prompt 缓存能命中，实验之间可以公平比较；
- **结构确实不变**：dw 库是 Phase 0 复制的固定数据。

**需要更新时**（数仓结构变化，生产环境会遇到）：
1. 删除 `runs/phase1/schema_dw.json`；
2. 再运行一次 `python scripts/phase1.py dev`（或其他模式），自动从 Databricks 重新生成；
3. 更新线上平台：`python scripts/build_app_bundle.py`，然后 `python scripts/deploy_app.py --skip-secrets`。

注意：schema 变化后 prompt 随之变化，**旧的 LLM 缓存不再命中**，新旧运行结果也不能直接比较。

### 可以看作 context 吗？

可以，但要区分"原始材料"和"真正进入 prompt 的内容"：

| 层次 | 内容 | 是否进 prompt |
|---|---|---|
| schema_dw.json（全集） | 97 张表、1,530 列，是 context 的**来源** | 不会整体放入（全部渲染约 9.5 万字符） |
| 检索 + 渲染后的 schema（子集） | 每题 20 张表 + 补充的表，约 3.3 万字符 | **进 prompt**，是模型实际看到的 context |

放到整个项目的 context 体系里：

| context 来源 | 性质 | 何时变化 |
|---|---|---|
| **schema_dw.json**（表结构） | 数仓的结构事实 | 数仓结构变化时重新生成 |
| 生成规则 `RULES` | 数仓的通用约定（方言、统计函数写法） | 人工修改，改后换 prompt 版本号 |
| 相似题示例库（examples） | 已解题 | 外循环更新 |
| 数仓使用说明（`kb.json`） | 从已解题统计出的使用习惯 | 外循环重新统计时更新 |
| 当次运行的观察和诊断 | 本题的报错、诊断结论、修复证据 | 内循环每一轮都变 |

### 对设计的启示

外循环**不改 schema 本身**（结构是事实），而是在 schema 之上**另外叠加**经验层的 context（示例库、使用说明）。企业的语义层也是同样的关系：表结构来自数据库，业务说明和指标口径由人另外维护。

如果将来要给列加业务说明（比如"`DEPT_BUDGET_CODE` 是预算编码，不是院系代码"），合理做法是放在**单独的知识文件**里，而不是改 schema 文件，这样结构事实和人工知识能分开管理、分别追溯。

## 疑问 12：数仓使用说明（`kb.json`）"从已解题统计出的使用习惯、外循环重新统计时更新"是什么意思？

### 结论

`kb.json` 是**外循环产出的经验知识库**：从 5,656 道已解题的标准 SQL 里，统计出"这个数仓平时怎么用"，存成一个文件。生成 SQL 时，每道题从中挑出相关的几条，作为"数仓使用说明"放进 prompt。

- `schema_dw.json` 像**数据字典**：有哪些表、每张表有哪些列；
- `kb.json` 像**老员工的经验笔记**：这类问题平时用哪张表、两张表通常怎么连。

### 文件里有什么

路径 `runs/knowledge/kb.json`，约 350KB，由 [agent/knowledge.py](../agent/knowledge.py) 生成：

| 字段 | 含义 | 实际数据举例 |
|---|---|---|
| `n_queries` | 统计了多少道已解题 | 5,656 |
| `table_freq` | 每张表被多少道题用过 | `sis_department` 2,620 次，`course_catalog_subject_offered` 1,984 次 |
| `word_df` | 每个题干词出现在多少道题里 | `graduate` 308 道，`enrolled` 2,259 道 |
| `word_tables` | 题干出现某个词的题，用了哪些表 | 含 "graduate" 的 308 道题里：`sis_department` 278 次、`sis_course_description` 180 次、`mit_student_directory` 162 次 |
| `groups` | 相似表组（列名高度重合） | `academic_terms` / `academic_terms_all`，`library_subject_offered` / `tip_subject_offered` 等 4 组 |
| `joins` | 每对表的关联习惯 | `sis_department` 和 `tip_subject_offered`：750 道题里 899 次用 `DEPARTMENT_CODE = OFFER_DEPT_CODE`，INNER 879 次、LEFT 21 次 |
| `version` | 版本号 | `kb-v1` |

这些都是**计数**，不是大段文本，也不是某道题的答案。

### 怎么用

生成 SQL 时，[agent/generator.py](../agent/generator.py) 调用 `kb.notes_for(问题, 已选的表)`，按题干用词从计数中挑出相关的几条，转成 7–13 行文字放进 prompt：

```
Warehouse usage notes (counted from 5656 solved questions of this warehouse; conventions, not rules):
- Tables that solved questions with similar wording use most: sis_department (100%), tip_subject_offered (54%), ...
- Look-alike tables ... solved queries used: tip_subject_offered 74%, library_subject_offered 26%
- Join sis_department - tip_subject_offered: usually sis_department.DEPARTMENT_CODE =
  tip_subject_offered.OFFER_DEPT_CODE (899/900 of 750 queries), INNER JOIN (98%)
```

它针对错误分析中最大的两类错误：**选错相似的表**（38%）和**关联方式写错**（19%）。

### "外循环重新统计时更新"的含义

- **生成方式**：运行 `python scripts/build_knowledge.py`（约 1–2 分钟，不调用 LLM），读取训练集（评测集和开发集以外）的标准 SQL，逐条解析、计数，覆盖写入 `kb.json`。
- **运行时只读**：内循环（每道题的生成、修复）只读取，从不修改。
- **什么时候更新**：只有**重新运行 `build_knowledge.py`** 时，这就是外循环的一次"学习"。典型情况：
  1. 已解题库增加了新题（生产中即新的、经过审核的查询）；
  2. 改进了统计方法（比如增加新的知识类型），版本从 `kb-v1` 升到 `kb-v2`；
  3. 数仓结构变化后，旧统计可能过时。
- **更新后要验证**：回到开发集重新跑对比，确认效果变好才保留。上一次对比：glm 开发集答对 3 → 5。

### 和 `schema_dw.json` 的区别

| | `schema_dw.json` | `kb.json` |
|---|---|---|
| 内容 | 结构事实：表、列、类型、样例值 | 使用经验：常用哪些表、相似表怎么选、怎么关联 |
| 来源 | Databricks 表结构 + BEAVER 元数据 | 训练集已解题的标准 SQL |
| 是否用到 Gold | 不用 | 离线统计用训练集 Gold；运行时只读统计结果 |
| 何时更新 | 数仓结构变化时重新生成 | 外循环重新统计时 |
| 是否可选 | 必需（没有它 Agent 看不到数仓） | 可选：`--knowledge on`、配置 `knowledge.mode`、网页"数仓使用说明"开关 |

一句话：**schema 告诉模型"有什么"，kb 告诉模型"平时怎么用"。**

## 疑问 13：`notes_for` "取出本题相关的约 10 行"具体指什么？

### 结论

指 `notes_for` 为一道题生成的那段"数仓使用说明"文字。行数**不是固定取 10 行**，而是按规则拼出来的，每题不同。在开发集 30 题上实测是 **7–13 行，大多数题 12–13 行**，"约 10 行"的说法不够准确。

### 这段文字由四部分组成

[agent/knowledge.py](../agent/knowledge.py) `notes_for(question, schema_tables)`：

| 部分 | 行数 | 怎么选出来 |
|---|---|---|
| ① 标题 | 1 | 固定：说明这是从 5,656 道已解题统计出的约定，不是硬性规则 |
| ② 常用表 | 1 | `table_scores` 按题干用词给表打分，**只保留已在 schema 里的表**，取前 6 张，按比例列出 |
| ③ 相似表 | 0–4 | 对 4 组相似表逐组检查：组里至少 2 张在 schema 中、且至少 1 张进了②的前 6，就输出本组内的使用比例 |
| ④ 关联习惯 | 0–8 | 在②的 6 张表之间两两查找统计过的关联，按"一起出现的题数"排序，取前 8 对，输出常用关联键和 INNER / LEFT |

上限为 1 + 1 + 4 + 8 = 14 行。开发集实测分布：7 行 1 题、9 行 1 题、10 行 1 题、11 行 3 题、12 行 13 题、13 行 11 题。

### "本题相关"怎么判断

1. **按题干用词**：`table_scores` 看问题里的词（IDF 加权），在已解题中指向哪些表；
2. **只谈 schema 里已有的表**（`if t in shown`）：不提模型看不到的表，避免"说了但没法用"。

### 实际例子：dw_4188（13 行）

题目大意：按学年和院系，统计工程学院的最少选课人数、材料记录数、方差、标准差……

```
① Warehouse usage notes (counted from 5656 solved questions ...; conventions, not rules):
② - Tables that solved questions with similar wording use most: tip_detail (100%), course_catalog_subject_offered (94%),
     academic_terms (91%), tip_subject_offered (91%), academic_terms_all (90%), subject_offered_summary (58%)
③ - Look-alike tables ...: academic_terms 50%, academic_terms_all 50%
③ - Look-alike tables ...: course_catalog_subject_offered 85%, cis_course_catalog 15%
③ - Look-alike tables ...: tip_subject_offered 62%, library_subject_offered 38%
④ - Join academic_terms - course_catalog_subject_offered: usually ...TERM_CODE = ...TERM_CODE (474/919 of 710 queries), INNER JOIN (100%)
④ - Join academic_terms_all - course_catalog_subject_offered: ...
④   ……共 8 行关联
```

### 暴露的局限

- **按词判断比较粗**：②的 6 张表都和"学年、课程、选课人数"这类词有关，但这道题 Gold 实际要用的 `sis_department`、`library_material_status` 没排进前 6，说明文字也没提它们。题干词多时，得分容易被常见的课程类表占据。
- **相似表比例有时没有倾向**：`academic_terms` 与 `academic_terms_all` 各 50%，提供不了有效信息。
- **关联行占大半**：13 行里 8 行是关联；如果前 6 张表本身选得不准，这些关联信息的价值也打折扣。

### 可以改进的地方

- ②从"按词打分"改为"按相似题统计"：直接看相似的几道已解题用了哪些表，与 examples 的检索结果对齐；
- 相似表比例接近五五开时不输出这一行；
- 关联行只保留与②中前几张表有关的，减少篇幅。

这些改动都需要在开发集上重新对比，才能确认效果。

## 疑问 14：`gen = self.generator.generate(task, retrieval.tables)` 除了生成 SQL，会去执行 SQL 吗？调用关系是什么？

### 结论

**不会。`generate` 只负责"写出 SQL"，不执行。** 它只调用 LLM，不连接数据库，内部也没有执行器。SQL 的执行在之后 controller 的循环里，由 `_execute` → 执行器完成。

### `generate` 里做了什么

[agent/generator.py](../agent/generator.py) `FewShotGenerator.generate`：

```python
def generate(self, task, tables, oracle_hints=None):
    examples = self.examples
    if self.index is not None:                                  # ① 相似题示例（可选）
        hits = self.index.top(task.question, self.k)
        examples = [h.example for h in hits]
        tables = tables + 示例用到、但检索没选出的表[:6]
    notes = self.knowledge.notes_for(...) if self.knowledge else ""   # ② 数仓使用说明（可选）
    prompt = build_prompt(task, render_schema(self.catalog, tables), examples, oracle_hints, notes)  # ③ 拼 prompt
    r = self.client.complete(prompt, system=SYSTEM)             # ④ 调用 LLM
    sql, status = extract_sql(r.text)                           # ⑤ 抽出 SQL 文本
    return Generation(sql, r.text, status, r, prompt, ...)      # ⑥ 返回，不执行
```

返回的 `Generation` 只有：SQL **文本**、模型原始回答、解析状态（OK / NO_SQL / EMPTY_RESPONSE）、token 用量、prompt、所用示例、schema 里的表、使用说明。**没有执行结果。**

### 执行发生在哪里

[loop_engineer/controller.py](../loop_engineer/controller.py) `run`：

```python
gen = self.generator.generate(task, retrieval.tables)       # 只生成 SQL
attempt = {..., "generated_sql": gen.sql, "parse_status": gen.parse_status, ...}
for n in range(1, self.cfg.max_attempts + 1):
    exe, rows = self._execute(attempt["generated_sql"], task.db, attempt["parse_status"])   # ← 这里才执行
    decision = verifier.verify(attempt, rows)                # 自检
    ...（未通过 → 观察、诊断、修复，得到新 SQL，下一轮再执行）
```

`_execute`：

```python
def _execute(self, sql, db, parse_status):
    if not sql:                                            # 没抽出 SQL，不执行
        return {"execution_status": parse_status, ...}, []
    ex = self.executor.execute(sql, db, max_rows=...)      # 调用执行器
    ...
```

最终到 [execution/databricks_sql.py](../execution/databricks_sql.py) `DatabricksSqlExecutor.execute`：只读检查 → 切换到 `dw` 库 → 在 SQL Warehouse 执行 → 超过行数上限返回 `TOO_MANY_ROWS` → 出错时提取错误类别。

### 完整调用关系

```
LoopController.run
├─ retriever.retrieve(question, 20)          检索表      不连数据库、不调 LLM
├─ generator.generate(task, tables)          生成 SQL    只调 LLM
│   ├─ index.top(...)                        相似题示例（可选）
│   ├─ knowledge.notes_for(...)              使用说明（可选）
│   ├─ build_prompt(... render_schema(...))  拼 prompt
│   ├─ client.complete(prompt, system)       调用 LLM（缓存 → HTTP）
│   └─ extract_sql(r.text)                   抽出 SQL 文本
└─ for n in 1..max_attempts:
    ├─ _execute(sql)                         执行        只连数据库
    │   └─ executor.execute(sql, db)         Databricks SQL Warehouse
    ├─ verifier.verify(attempt, rows)        自检
    └─（未通过）observe → diagnose → route → skill.repair（新 SQL，下一轮再执行）
```

### 为什么这样分开

| 原因 | 说明 |
|---|---|
| 职责单一 | 生成器只管"写"，执行器只管"跑"，Loop 决定跑完之后做什么（自检、诊断、修复） |
| 修复后要重新执行 | 修复技能产生的新 SQL 也要执行；执行放在循环里，第 1 次生成和之后每次修复的 SQL 走同一个 `_execute`，处理方式完全一致 |
| 便于测试 | 单元测试可用假的执行器（如 `tests/test_phase6.py` 的 `Exec`），不连数据库也能测 Loop 逻辑 |
| 两组实验公平 | 生成只做一次且会被缓存，两个实验组的第 1 条 SQL 相同，差别只出现在执行之后的处理 |

基线运行（`evaluation/baseline.py` 的 `run_case`）也是同样的顺序：先 `generator.generate`，再 `executor.execute`，只是执行一次后直接判分，没有修复循环。

# 设计定位类疑问

## 疑问 15：代码里只看到内循环（每道题错了就修复），外循环在执行过程中的逻辑在哪里？Loop Engineering 的核心在内层还是外层？

### 结论

- **现状**：代码里只有内循环是真正自动运行的；**外循环目前是人工分几步完成的流程**，每一步都有脚本支撑，但串起来、做判断的是人。这是项目当前的一个真实缺口。
- **核心在哪层**：两层都是 Loop Engineering，但价值来源不同。**内循环负责"可靠性"，外循环负责"进化"**。本项目数据表明，准确率的提升来自外循环。

### 现状：外循环是人工驱动的流程

| 步骤 | 谁做 | 用的工具 |
|---|---|---|
| 1. 跑一批题 | 人执行命令（或网页上点） | `phase1.py` / `phase6.py` / 网页 |
| 2. 分析错因 | 人执行脚本、读结果、分类 | `analyze_run.py` |
| 3. 决定补什么知识 | **人判断**（如"选错表占 38%，所以补用表约定"） | — |
| 4. 构建知识 | 人执行脚本 | `build_knowledge.py`、相似题示例库 |
| 5. 回开发集验证 | 人执行、人对比 | `phase1.py --knowledge on` |
| 6. 决定保留与否、记录 | **人判断**，写 EXECUTION_LOG | — |

另外，`build_knowledge.py` 目前是对全部训练集做**静态统计**，并不依赖"系统错在哪"，还不是"根据失败学习"的循环。

### 内循环与外循环的对比

| | 内循环 | 外循环 |
|---|---|---|
| 时间尺度 | 一道题之内，秒级 | 跨一批题、跨版本，天级 |
| 反馈信号 | 执行报错、自检结果（不看 Gold） | 判分结果、错误分析（离线可用 Gold） |
| 改变的是什么 | 这一道题的 SQL | 系统本身：知识、示例、规则、参数 |
| 本项目实测效果 | 能执行的题增加（glm 4→9，DeepSeek 24→29），**答对数不变** | glm 答对 0 → 3 → 5；DeepSeek + Loop 3 → 8 |
| 定位 | 兜底：修显式失败 | 提升：让系统越来越少犯同类错误 |

外循环才是 Loop Engineering 区别于"写一个 retry"的地方，也是面试中最有价值的部分，而它目前还是手工流程。

### 改进方案：把外循环做成代码（`scripts/outer_loop.py`，已实现，见文末“实现情况”）

一次迭代由**错误驱动**：

```
① 采样：从训练集抽一批题（如 100 道，不碰开发集和评测集）
② 运行：用当前配置跑这批题（glm 免费）
③ 诊断：逐题对照 Gold，自动分类错因（复用 analyze_run 的逻辑）
④ 归纳：只针对错题生成候选知识，例如
     - 选错相似表 → "问到 X 类概念时，用表 A 而不是表 B"（附统计支持度）
     - 关联写错 → "表 A 与 B 通常用键 K、LEFT JOIN"
     - 列挂错表 → "列 C 在表 T 里"
⑤ 验证：在开发集上重跑，检查是否退步
⑥ 采用：写入新版本知识库（保留旧版本可回滚），生成本次迭代的报告
```

| | 现在 | 做成外循环之后 |
|---|---|---|
| 知识从哪来 | 对全部训练集静态统计 | 从**系统实际犯的错**中归纳，针对性更强 |
| 谁决定采用 | 人看数字 | 自动门禁 + 人审核（见疑问 16） |
| 能否重复 | 人按顺序执行多个命令 | 一条命令跑一次迭代，可多次迭代 |
| 可追溯 | 靠 EXECUTION_LOG 人工记录 | 每次迭代自动生成报告：学了什么、依据哪些错题、开发集效果 |

纪律不变：学习只用训练集，开发集只当门禁，评测集不碰。成本：每次迭代约 100 道训练题 + 30 道开发题，约 130 次 glm 调用，免费。

## 疑问 16：这样设计外循环，符合公司的实际设计逻辑吗？

### 结论

大方向符合，但有一处要调整：**公司里外循环通常不全自动地改线上知识，而是"系统自动提出建议，人审核后才上线"**，也就是"评测驱动 + 人在环路"。

> 依据为公开的产品文档和工程博客（截至 2026 年中），各家具体做法差别不小。

### 公司里外循环通常怎么做

| 环节 | 常见做法 | 例子 |
|---|---|---|
| 收集信号 | 线上反馈：点赞 / 点踩、采纳还是改写 SQL、追问、人工抽检；查询日志 | Genie 的反馈按钮；Vanna 把用户确认的"问题-SQL"加入库 |
| 分析错因 | 看 trace、按错因聚类，部分用 LLM 辅助归纳 | 各家的可观测平台 |
| 产出改进 | 补表 / 列说明、加已验证查询、调整指令、改语义层定义 | Genie 的空间说明和示例 SQL；Cortex Analyst 的语义模型和已验证查询库 |
| 上线前验证 | 跑基准问题集做回归，准确率不降才上线 | Genie 的基准问题功能 |
| 谁做决定 | **数据负责人或分析师审核批准** | 语义层、已验证查询由人维护 |
| 上线后 | 监控采纳率、报错率，出问题回滚 | — |

分工：**机器负责发现问题、提出候选改进、自动回归；人负责判断和批准。**

### 方案中符合的部分

| 方案 | 对应公司做法 | 是否符合 |
|---|---|---|
| 从错误出发归纳知识 | 按错因聚类，针对性补知识 | ✅ |
| 知识放在上下文，不改模型 | 语义层、已验证查询库 | ✅ |
| 开发集当门禁，不退步才采用 | 基准问题集回归 | ✅ |
| 知识带版本、可回滚 | 配置版本管理 | ✅ |
| 每条知识附统计依据和来源题目 | 可审核、可追溯 | ✅ |

### 需要调整的部分

**1. 不自动上线，加人工审核**

原方案"开发集不退步就自动写入新版本"在公司里一般不会这样做：
- **开发集太小**：30 题上的波动很容易是偶然的，自动采用可能把噪声当成改进；
- **知识可能错**：把某道题的特殊情况泛化成通用规则，影响所有问题；
- **责任和合规**：指标口径、用表约定属于业务定义，需要有人负责；
- **自我强化的风险**：系统根据自己的输出学习，错误可能被越放越大。

调整：外循环产出"**候选知识 + 证据 + 回归结果**"报告，人审核通过后才合并。实际实现为：`scripts/outer_loop.py` 生成待审核提案，审核页批准后生效（见本节末"实现情况"）。

**2. 说清楚学习信号的来源**

- 本项目用训练集的 Gold 当"老师"（BEAVER 有约 5,600 道带标准答案的题）；
- 公司一般没有这么多标准答案，信号来自**用户反馈、已验证查询、人工抽检**。

训练集在这里**模拟的是"已验证查询日志"**：外循环结构不变，换成真实反馈数据源就能用。这个"信号源可替换"的设计，比全自动更贴近实际。

**3. 门禁不只看准确率**

回归条件应包括：答对数不减少、原来答对的题不变错（不误伤）、token 增幅在阈值内。

### 调整后的外循环

```
① 采样训练集（模拟"已验证查询日志"）→ ② 用当前配置运行 → ③ 对照标准答案找错因、聚类
→ ④ 生成候选知识（附支持度和来源题目）→ ⑤ 开发集回归（准确率、误伤、成本；逐条回归）
→ ⑥ 生成审核报告 ──人审核──▶ ⑦ 批准的条目合并进新版本知识库（可回滚）
```

自动化：①–⑤ 和报告；人负责：⑥ 审核批准；上线：⑦。

### 面试回答参考

> "外循环参照企业做法设计成'评测驱动 + 人在环路'：系统自动从失败中归纳候选知识、自动跑开发集回归、输出带证据的报告，由人批准后才合并进知识库，知识有版本、可回滚。我没有做全自动更新，因为开发集小、知识可能过度泛化，而且业务口径需要有人负责。在 BEAVER 上，我用训练集的标准答案模拟企业的'已验证查询日志'；换到生产环境，把信号源换成用户反馈和人工抽检即可，结构不变。"

### 实现情况（2026-09-30）

按"公司落地形式"重新组织了系统，五点设计与实现对应如下：

| 设计 | 实现 |
|---|---|
| 1. 开放用户提问界面，结果可点赞 / 点踩 | 网页「提问」页：提问 → 内循环作答（只用自检，没有 Gold）→ 👍 / 👎、原因、可选的修正 SQL（先只读执行校验）、备注 |
| 2. 每次提问采集 trace 和反馈，作为外循环的上下文 | `experience.user_queries`（问题、最终 SQL、每次尝试）和 `experience.feedback`（每个问题取最新一条） |
| 3. 外循环评估后不直接改，先交给数据工程师决定 | `scripts/outer_loop.py` 生成提案 → 开发集回归门禁 → `experience.proposals`（待审核）→「审核」页批准后写入 `experience.knowledge_items`，下一次提问即生效；可随时停用回滚。邮件通知以后再加 |
| 4. 内层循环仍是单题 SQL 修复 | 不变，提问页和评测用同一个 `build_controller` |
| 5. 用户问题只有内循环，评测集两层都有 | 用户问题：只走内循环，反馈离线进入外循环；有 Gold 的数据：训练集用于学习、开发集用于门禁；评测集只在配置冻结后做定期报告，不参与每次迭代 |

与原设想的两处差异：
- **门禁用开发集而不是评测集**：评测集每次迭代都跑，就等于在评测集上调参，最终分数会偏高。
- **用户反馈不直接变成知识**：👍 的答案、修正 SQL 只是"候选已验证查询"，同样要经审核才进入示例库。

## 疑问 17：能不能把用户的问题和反馈直接存进一个 context 里使用？这符合市场上项目的逻辑吗？

### 结论

可行，也符合市场做法，但要看"存进 context"具体指什么。关键不在"存不存"，而在两个设计选择：**谁能写进去**、**对谁生效**。

### 三种"context"

| 做法 | 可行性 | 市场上是否这样做 |
|---|---|---|
| **A. 把历史问题和反馈全部塞进每次的 prompt** | 不可行 | 基本没人这样做：数据一多就超出上下文长度，成本高，无关内容还会干扰模型 |
| **B. 存进一个"经验库"，提问时检索相似的几条放进 prompt** | 可行 | **主流做法**，本质是 RAG：查询日志和已验证查询库 |
| **C. 会话内上下文**：同一次对话里前几轮的问题和答案 | 可行 | 很常见，用来支持追问（"那按院系拆开呢？"） |

本项目现在的"已验证查询进入相似题示例库"就是 B 的一种。

### 市场产品的通行逻辑：按可信度和作用范围分层

> 依据为公开的产品文档（截至 2026 年中），各家细节不完全相同。

| 产品 | 反馈怎么用 |
|---|---|
| Databricks Genie | 用户点赞 / 点踩；空间作者据此把好的 SQL 加为示例（trusted assets），匹配时界面标"可信" |
| Snowflake Cortex Analyst | 已验证查询库（verified query repository），由管理员确认后加入 |
| Vanna 等开源框架 | "问题 + 正确 SQL"加入训练库；可配置为用户确认后自动加入，但建议先人工把关 |

共同模式是两级：

```
原始反馈（自动采集，未验证）
  → 记录：用于统计、分析、生成候选
  → 不直接影响其他人的答案
        │ 人工确认
        ▼
已验证知识（组织级）
  → 所有人提问时都会检索到
  → 界面标"已验证"
```

**点踩（👎）几乎不会直接进上下文**，它的作用是提示"这里有问题"，交给人排查。

### 为什么组织级的内容一般要审核

1. **👍 是弱信号**：用户看着像对就点了，不等于真对；在 BEAVER 上"能执行但答错"的比例本来就高。
2. **错误会自我放大**：错的示例被检索到，相似问题跟着错，错的答案又可能再被点赞。
3. **权限问题**：A 用户的问题和结果可能包含 B 用户无权查看的数据，不能无差别共享。
4. **责任归属**：指标口径属于业务定义，需要有人负责。

### 放到本项目：三层"经验库"

问题和反馈存成**一条统一记录**是合理的数据模型，只要带上"可信度"和"作用范围"两个字段：

| 层 | 内容 | 谁能写入 | 对谁生效 | 现状 |
|---|---|---|---|---|
| 会话上下文 | 本次对话前几轮的问答 | 自动 | 只在当前对话 | ❌ 提问页目前是单轮 |
| **个人经验** | 这个用户自己 👍 过的答案、自己改过的 SQL | **自动，不审核** | **只对这个用户** | ❌ 未做 |
| 组织知识 | 已验证查询、选表偏好、补表提示、关联规则 | 审核后 | 所有人 | ✅ 已有（外循环 + 审核页） |

"个人经验"这一层最接近"直接存进 context"的想法：
- **不审核、立即生效**：下次问类似问题时检索出来，标注"你之前确认过的查询"；
- **风险可控**：即使错了，也只影响这个用户自己；
- **逐级升级**：被很多人确认的条目，再作为候选进入外循环，审核后升级为组织知识。

即"**自动采集、分级生效、逐级升级**"：系统能马上"记住"用户，又不让未经验证的内容污染所有人的答案。

### 面试回答参考

> "用户反馈我存成统一的经验记录，带可信度和作用范围。未经验证的只对提问者本人生效，作为个人记忆检索；被多人确认的进入外循环候选，经开发集回归和人工审核后才升级为组织级的已验证查询。这和 Genie、Cortex Analyst 的已验证查询机制是同一个思路。我没有让反馈直接对所有人生效，因为点赞是弱信号，错误会通过检索自我放大，还涉及数据权限。"

## 疑问 18：企业是怎么实现 Loop 的？用户问了一道题，系统是不是也只能检测 SQL 语法错误，识别不了语义错误？

### 结论

基本是这样：**线上没有标准答案时，语法和执行错误能可靠检测，语义错误只能部分检测**。这是行业共识，不是本项目特有的问题。企业不指望"事后查出所有语义错误"，而是组合四类手段：**事前预防、部分检测、让用户能核对、离线持续评估**。

> 依据为公开的产品文档和技术分享（截至 2026 年中），各家具体实现不完全公开，细节会有差异。

### 能检测到什么程度

| 错误类型 | 线上能否自动发现 | 手段 |
|---|---|---|
| 语法错误、列 / 表不存在、类型错误 | ✅ 可靠 | 执行报错 |
| 结果明显异常：空结果、行数爆炸、全是 NULL | ✅ 基本可靠 | 结果检查 |
| 结构性错误：关联条件恒为真、缺分组、统计量自相矛盾 | 🟡 部分 | 规则检查、数值一致性（本项目已做） |
| 过滤值不存在、关联导致重复计数 | 🟡 部分 | 查库验证（本项目做过评估） |
| **口径理解错**："活跃用户"按登录还是按下单算？"收入"含不含退款？ | ❌ 基本不能 | 只能靠事前定义口径，或让用户核对 |
| **选错相似表**：用了历史表而不是当前表 | ❌ 很难 | 靠事前告诉模型该用哪张 |

后两类正是 BEAVER 上"能执行但答错"的主体。判断它们对不对的标准在**业务定义**里，不在 SQL 或结果里，所以只看 SQL 和结果的检查都无能为力。

### 企业的四类手段

**① 事前预防（最主要的手段）**：让模型一开始就少犯语义错误，而不是事后检测。

| 做法 | 说明 | 例子 |
|---|---|---|
| 语义层 | 数据团队预先定义指标、维度和表之间的关联，模型基于定义生成，而不是对着原始表猜 | Snowflake Cortex Analyst 语义模型、dbt Semantic Layer、Looker LookML |
| 已验证查询库 | 常见问题的正确 SQL 由人审核后存起来，新问题足够相似时复用，并标"已验证" | Cortex Analyst verified queries、Genie 示例 SQL |
| 空间 / 领域限定 | 一个问答空间只开放少数相关表，并附业务说明 | Databricks Genie space |

本项目的数仓使用说明和审核知识大致相当于轻量语义层。区别在于：企业的语义层是**人写的明确定义**，本项目的是从已解题**统计出来**的约定。

**② 运行时部分检测（给出置信度，而不是断定对错）**

| 做法 | 原理 | 局限 |
|---|---|---|
| 多候选一致性 | 生成多条 SQL 分别执行，结果一致则置信度高，不一致则提示可能有歧义 | 成本成倍增加；多个候选可能犯同样的错 |
| LLM 审查 | 另一个模型对照问题审查 SQL | 误报高（本项目实测 DeepSeek 抓错 27/30，但把 31/33 个正确答案也判错） |
| 查库验证 | 检查过滤值是否存在、关联是否导致重复计数 | 只覆盖特定错误类型 |
| 规则 / 数值检查 | 结构和数值上必然成立的关系 | 零误报，但覆盖面窄 |

置信度低时，系统提示用户、请求澄清或转人工，而不是自动断定"错了"再去修。

**③ 让用户能核对（把语义判断交还给懂业务的人）**

- **展示 SQL 和解读**：用自然语言说明"我是怎么理解你的问题的"（如"'上季度'按自然季度，'收入'不含退款"），用户一眼能看出口径对不对；
- **主动澄清**：问题有歧义时先问（"'活跃'是指登录还是下单？"），Genie、Cortex Analyst 在问题不明确时都会澄清或给出建议问题；
- **反馈按钮**：点赞 / 点踩进入外循环；
- **标注可信度**：命中已验证查询的答案标"已验证"，其余提示"请核对"。

**④ 离线持续评估（外循环）**：维护基准问题集，每次改动回归测试（Genie 有这个功能，对应本项目的开发集 / 验证集门禁）；监控点踩率、改写率，按错因聚类，补知识。

```
事前预防（语义层、已验证查询） ─▶ 大幅减少语义错误          ← 主力
运行时检测（执行、规则、多候选、审查）─▶ 发现显式错误 + 给出置信度
用户核对（解读、澄清、反馈）  ─▶ 语义对错由懂业务的人判断
离线评估（基准集、反馈分析）  ─▶ 持续补知识                 ← 外循环
```

因此，"内循环只能修显式错误，语义正确性靠知识和人"**正是企业系统的现实结构**，不是本项目做得不够。

### 对照本项目：已有什么，还能补什么

| 手段 | 状态 |
|---|---|
| 执行报错、结果、结构、数值检查 | ✅ 已有（内循环） |
| 统计知识 + 审核知识 + 已验证查询 | ✅ 已有（相当于轻量语义层） |
| 反馈 + 外循环 + 门禁 + 审核 | ✅ 已有 |
| LLM 审查、查库验证 | 已评估，只作提示 |
| 多候选一致性（给置信度） | ❌ 未做，可作下一个实验 |
| 用自然语言说明"我是怎么理解的" | ❌ 未做，产品价值高、实现成本低 |
| 有歧义时主动澄清 | ❌ 未做 |

### 面试回答参考

> "线上没有标准答案，自动检测只能可靠覆盖语法、执行和结构性错误；口径类语义错误的判断标准在业务定义里，SQL 本身看不出来。所以我按企业的做法分工：内循环修显式错误；语义正确性靠事前的知识（统计出的使用说明、审核过的规则和已验证查询，相当于轻量语义层）和外循环持续补充；运行时的 LLM 审查、查库验证我都做了离线评估，误报太高的只作提示。产品上还可以加'解释我的理解'和主动澄清，把最终的语义判断交给懂业务的用户。"

## 疑问 19：`Diagnoser.diagnose` 函数是怎么工作的？

### 结论

`diagnose`（[loop_engineer/diagnose.py:186](../loop_engineer/diagnose.py#L186)）回答"这次尝试**为什么**失败"，采用**两级策略**：先用规则，规则判断不了再问 LLM。

```python
def diagnose(self, obs: Observation) -> tuple[Diagnosis, dict[str, Any]]:
    d = diagnose_by_rules(obs, self.catalog)                     # ① 规则
    if d is not None:
        return d, {}
    if self.client is None:                                      # ② 没配 LLM
        return Diagnosis(UNKNOWN, 0.0, "no explicit signal and no LLM stage", "fallback"), {}
    prompt = LLM_PROMPT.format(question=..., tables=..., sql=..., status=..., rows=..., preview=...[:600])  # ③
    r = self.client.complete(prompt, system=LLM_SYSTEM)          # ④ 调 LLM
    usage = {"input_tokens": ..., "output_tokens": ..., "latency_ms": ..., "cached": ...}
    parsed = parse_llm_diagnosis(r.text)                         # ⑤ 解析
    if parsed is None:
        return Diagnosis(UNKNOWN, 0.0, f"unparseable LLM answer: {r.text[:120]}", "llm"), usage
    ft, conf, reason = parsed
    return Diagnosis(ft, conf, reason, "llm", {"signal": "llm"}), usage   # ⑥
```

### 输入和输出

- **输入** `obs`：`observe` 产出的观察结果，只含 Agent 可见信息和从报错中解析出的信号。
- **输出**：`(Diagnosis, usage)`。`usage` 是这次诊断的 LLM 用量，没调 LLM 时为 `{}`。

| `Diagnosis` 字段 | 例子 |
|---|---|
| `failure_type` | `COLUMN_MAPPING_FAILURE`（6 类，外加 `UNKNOWN`） |
| `confidence` | `0.9` |
| `reason` | "TERM_CODE exists in academic_terms, which the SQL already uses, but was referenced through another alias" |
| `source` | `rule` / `llm` / `fallback` |
| `repair_hints` | `{"column": "TERM_CODE", "qualifier": "sd", "owner_tables": [...], "suggestions": [...], "case": "wrong_alias"}` |

### 逐步拆解

**① 规则诊断** `diagnose_by_rules`（[diagnose.py:83](../loop_engineer/diagnose.py#L83)）：按顺序检查明确信号，命中即返回，不调 LLM。

| 信号 | 诊断 |
|---|---|
| 没生成 SQL | 执行错误（0.9） |
| 列找不到：到表结构目录里查这一列属于哪张表 | 在 SQL 已用的表里 → 列映射，别名挂错（0.9）<br>在检索到但没用的表里 → 选表（0.8）<br>只在没检索到的表里 → 选表（0.85）<br>哪张表都没有 → 列映射，编造列名（0.7） |
| 表不存在 | 选表（0.8） |
| 结果超过 50 万行 | 关联键（0.6） |
| 其他执行报错 | 执行错误（语法 / 聚合 / 窗口等 0.8，其余 0.6） |
| 自检发现的结构 / 数值问题 | 按 `_VERIFIER_TYPES` 映射，如关联条件恒为真 → 关联键；平均值不在最小最大之间 → 查询拆解 |

都不符合时返回 `None`。

**② 没配 LLM**：`Diagnoser(catalog, client=None)` 只用规则，判断不了就返回 `UNKNOWN`（来源 `fallback`），路由表交给 RepairSQL。用于"只用规则诊断"的对照实验。

**③ 组 LLM prompt**：走到这一步的典型情况是 SQL 执行成功但自检不通过、又没有可映射的检查结果，即**结果为空**、**某列全是 NULL**；`TIMEOUT`、`REJECTED` 也会落到这里（规则只处理 `ERROR`）。prompt（`LLM_PROMPT`，[diagnose.py:137](../loop_engineer/diagnose.py#L137)）包含 6 种失败类型的定义、问题、可用表、SQL、执行状态、行数、前几行结果（截断到 600 字符），要求只输出 `{"failure_type", "confidence", "reason"}` 的 JSON。

**④ 调 LLM**：与生成、修复共用同一个 `CachingChatClient`，同样有缓存和预算。`usage` 回到控制器，计入 `diag_tokens`：诊断不算一次 SQL 尝试，但计入成本。

**⑤ 解析** `parse_llm_diagnosis`（[diagnose.py:163](../loop_engineer/diagnose.py#L163)），防御模型不守格式：
- 正则 `\{.*\}` 取出 JSON，模型前后多说几句也能取到；
- JSON 解析失败 → `None`；
- `failure_type` 必须是 6 类之一，所以 LLM 不能给 `UNKNOWN`，编造的类型也会被拒；
- `confidence` 限制在 0–1，不是数字时取 0.5；`reason` 截断到 500 字符。

解析失败时返回 `UNKNOWN`（来源 `llm`），原因里附模型回答的前 120 字，便于排查。

**⑥ 返回**：LLM 诊断的修复线索只有 `{"signal": "llm"}`，不像规则诊断那样带具体的列、表和候选项，这是 LLM 诊断后修复效果差的原因之一。

### 在控制器里的用法

```python
diag, usage = self.diagnoser.diagnose(obs)
emit("diagnose", failure_type=..., confidence=..., reason=..., source=..., repair_hints=...)   # 网页"诊断"一步
route = self.policy.route(diag)                                       # 按 failure_type 选技能
res = self.policy.skill(route.skill).repair(obs, diag, self.ctx)      # 技能读 diag.repair_hints
nxt["diag_tokens"] = usage.get("input_tokens", 0) + usage.get("output_tokens", 0)
```

### 效果数据（Phase 4，评测集 87 个失败）

| 来源 | 题数 | 严格准确率 | 宽松准确率 |
|---|---|---|---|
| 规则 | 68 | 51.5% | **76.5%** |
| LLM（glm-4-flash） | 19 | 0/19 | 6/19 |

这是"先规则、后 LLM"的依据：有明确信号时，规则又快又准又免费；没有明确信号时，LLM 判断在弱模型上基本不可靠，只作兜底。

### 面试回答参考

> "诊断分两级。报错信息里有结构化信号时用规则，比如列找不到，就去表结构里查这一列属于哪张表，从而区分'别名挂错'和'少用了表'，还把列名、候选列这些证据作为修复线索传给技能。只有 SQL 能跑、但结果为空这类没有明确信号的情况，才问 LLM，并要求严格 JSON、校验类型。实测规则诊断宽松准确率 76.5%，LLM 诊断在 glm 上 19 题里严格一题都没对，所以 LLM 只作兜底。"

## 疑问 20：`res = self.policy.skill(route.skill).repair(obs, diag, self.ctx)` 里的 `self.ctx` 是怎么维护的？技能内部是不是调用完修复函数后，又调用了 LLM 生成 SQL？

### 一、`self.ctx` 怎么维护

**创建一次，之后不再修改。** `ctx` 是 `RepairContext` 对象，在组装控制器时创建，作为控制器字段保存：

```python
# scripts/phase6.py:106（命令行）
LoopController(..., RepairContext(catalog, client, examples), ...)
# app/runner.py:227（网页运行页和提问页，build_controller）
RepairContext(bundle.catalog, client, bundle.examples)
```

```python
@dataclass
class RepairContext:                       # skills/base.py:23
    catalog: SchemaCatalog                 # 表结构目录（schema_dw.json）
    client: ChatClient                     # LLM 客户端（带缓存和预算，与生成器、诊断器是同一个）
    examples: list[FewShotExample] = ...   # 固定的 3 个 few-shot 示例
    max_schema_tables: int = 24            # 修复 prompt 里最多放几张表
```

它只装"不随题目变化"的资源，而且都是 Agent 可见的，不含 Gold。**和某道题有关的信息**每次通过另外两个参数传入：

| 参数 | 内容 | 每次都变 |
|---|---|---|
| `obs` | 问题、上次的 SQL、执行状态、报错、解析出的信号、自检发现 | ✅ |
| `diag` | 失败类型、原因、修复线索（列名、候选列、要补的表……） | ✅ |
| `ctx` | 表结构、LLM 客户端、上限 | ❌ 固定 |

所以技能是无状态的，网页上多个运行在后台线程里共用同一个技能对象也不会互相干扰。

**一个发现：`ctx.examples` 没有被用到。** 所有技能只用了 `ctx.catalog`、`ctx.client`、`ctx.max_schema_tables`；`examples` 是 Phase 5 预留的字段，修复 prompt 里没有示例。

### 二、技能内部是不是"先修复、再调 LLM"

不完全是。技能的 `repair` 本身就是"修复"，内部分两段：**先做不用 LLM 的准备**（根据诊断整理定向信息，有的能直接确定性修好），**需要时再调一次 LLM 改写 SQL**。第二段统一走 `llm_repair`（[skills/base.py:85](../skills/base.py#L85)）：

```python
tables = [t for t in dict.fromkeys(tables) if t in ctx.catalog.tables][: ctx.max_schema_tables]
prompt = REPAIR_TEMPLATE.format(
    rules=RULES,                                      # 与生成时相同的 6 条规则
    schema=render_schema(ctx.catalog, tuple(tables)), # 技能挑选的表
    question=obs.question,
    sql=obs.generated_sql,                            # 上次的 SQL
    observed=observed_text(obs),                      # "执行失败：<报错>" 或 "检查发现：<问题>"
    diagnosis=f"{diagnosis.failure_type}: {diagnosis.reason}",
    instruction=instruction)                          # 技能写的定向指令：各技能的核心区别
r = ctx.client.complete(prompt, system=SYSTEM)        # 调 LLM
sql, status = extract_sql(r.text)                     # 抽出新 SQL
```

| 技能 | 不用 LLM 的部分 | 是否调 LLM |
|---|---|---|
| SchemaSearch | `fix_column_refs`：把挂错别名的列改到同一作用域里唯一拥有它的表 | **全部改好就不调**；有改不了的，才把部分修好的 SQL、候选列、相似列交给 LLM |
| RetrieveAgain | 找出拥有缺失列的表或名字相近的真实表，推断关联键 | 调 1 次 |
| FindJoinPath | 列出 SQL 里各表共享的键列 | 调 1 次 |
| ReplanQuery | 无（固定的"拆成子问题 / CTE"指令） | 调 1 次 |
| RepairSQL | 无（附 Databricks 语法限制说明） | 调 1 次 |

需要注意三点：

1. **技能里的 LLM 调用是"带着证据改写"，不是"重新生成"**：不调用生成器 `FewShotGenerator`，用的是修复模板，给模型看上次的 SQL、报错、诊断和定向信息。
2. **技能不执行 SQL**：只返回 `RepairResult.repaired_sql`，控制器把它作为下一次尝试，在下一轮开头执行、再自检。

```
技能返回新 SQL ─▶ 控制器：attempt = nxt ─▶ 下一轮：执行 → 自检 → 通过则结束，否则再观察、诊断、修复
```

3. **修复 prompt 缺少生成时的知识上下文**：

| 内容 | 生成 prompt | 修复 prompt |
|---|---|---|
| 规则 | ✅ | ✅ |
| schema | 检索 20 张 + 相似题补的 + 补表提示补的 | SQL 已用的 + 检索到的 + 技能补的（≤ 24 张） |
| 相似题示例 | ✅ 4 道 | ❌ |
| 数仓使用说明、审核知识 | ✅ | ❌ |
| 上次的 SQL、报错、诊断、定向指令 | — | ✅ |

修复时模型看不到外循环学到的知识，而选表错误恰恰最需要"同类问题通常用哪些表"。这可能是修复成功率不高的原因之一。**改进方向**：让修复 prompt 复用第 1 次生成时的相似题示例和说明，替换闲置的 `ctx.examples`，先在开发集上做对照实验。

### 面试回答参考

> "修复上下文在组装控制器时创建一次，只放表结构、LLM 客户端这类不随题目变化的资源；每道题的信息通过观察结果和诊断传入，所以技能是无状态的，可以并发共用。技能内部先做确定性工作，比如 SchemaSearch 能直接把挂错别名的列改对，完全不调 LLM；改不了的，再带着报错、诊断和技能整理的候选信息让 LLM 改写，技能本身不执行 SQL，由控制器下一轮执行和自检。梳理时我还发现修复 prompt 没带生成时的相似题和数仓说明，这是一个可以用对照实验验证的改进点。"

## 疑问 21：`replicate.py` 里"按列映射类型；MySQL 的 `_ci` 排序规则映射为 Databricks 的 `UTF8_LCASE`"这个函数的作用是什么？

### 结论

对应 [benchmark/beaver/replicate.py:57](../benchmark/beaver/replicate.py#L57) 的 **`map_column`**。它在 Phase 0 复制数据库时运行：**为 MySQL 的每一列决定在 Databricks 里用什么类型**，使复制后的数据在取值范围、精度、时区，尤其是字符串比较规则上与 MySQL 一致。这样同一条 Gold SQL 在两个引擎上才能得到相同结果。

### 输入和输出

```python
def map_column(c: MySqlColumn, collation_policy: str = "mirror_mysql_ci") -> ColumnMapping:
```

| 输入 `MySqlColumn`（来自 `information_schema.COLUMNS`） | 例子 |
|---|---|
| `name` | `DEPARTMENT_NAME` |
| `data_type` | `varchar` |
| `column_type` | `varchar(100)`、`int unsigned`、`decimal(10,2)` |
| `precision` / `scale` | `10` / `2` |
| `collation` | `utf8mb4_0900_ai_ci` |

| 输出 `ColumnMapping` | 作用 |
|---|---|
| `databricks_type` | 建表类型，如 `STRING COLLATE UTF8_LCASE`、`BIGINT`、`DECIMAL(10,2)` |
| `arrow_type` | 中间 Parquet 文件里的类型 |
| `staged_as_string` | 是否先以字符串暂存、插入时再 `CAST` |
| `note` | 映射时做的妥协，写进复制报告 |

### 映射规则

| MySQL 类型 | Databricks 类型 | 原因 |
|---|---|---|
| 整数 | 同级整数 | — |
| 整数 + `unsigned` | **放宽一级**（INT → BIGINT，BIGINT → DECIMAL(20,0)） | Databricks 没有无符号整数 |
| `decimal(p,s)`，p ≤ 38 | `DECIMAL(p,s)` | — |
| `decimal(p,s)`，p > 38 | `DECIMAL(38,s)`，先存字符串再转换 | Databricks 精度上限 38 |
| `float` / `double` | `FLOAT` / `DOUBLE` | — |
| `date` | `DATE` | — |
| `datetime` / `timestamp` | `TIMESTAMP_NTZ`，先存字符串 | MySQL DATETIME 无时区，避免会话时区偏移 |
| `year` | `INT` | — |
| `time` | `STRING`（`HH:MM:SS`） | Databricks 没有 TIME 类型 |
| 二进制 | `BINARY` | — |
| **字符串，排序规则以 `_ci` 结尾** | **`STRING COLLATE UTF8_LCASE`** | 见下文 |
| 字符串，其他排序规则 | `STRING` | — |
| 未知类型 | `STRING`，记 note | 兜底 |

### 重点：`_ci` → `UTF8_LCASE`

**问题**：MySQL 字符串列通常带 `_ci`（case-insensitive）排序规则，`WHERE DEPARTMENT_NAME = 'mathematics'` 能匹配到 `'Mathematics'`；Databricks 默认 `STRING` 区分大小写，同一条 Gold SQL 就匹配不到。影响的不只是 `=`，`GROUP BY`、`DISTINCT`、`COUNT(DISTINCT)`、`IN`、排序都会不同：MySQL 把 `'ABC'` 和 `'abc'` 当成同一个值。

**做法**：

```python
if t in _STRINGS:                                         # char / varchar / text / enum ...
    coll = (c.collation or "").lower()
    if collation_policy == "mirror_mysql_ci" and coll.endswith("_ci"):
        return ColumnMapping(c.name, c.column_type, "STRING COLLATE UTF8_LCASE", pa.string(), False,
                             "UTF8_LCASE mirrors case-insensitivity; accent-insensitivity/PAD SPACE not mirrored")
    return ColumnMapping(c.name, c.column_type, "STRING", pa.string(), False)
```

`UTF8_LCASE` 是 Databricks 忽略大小写的排序规则。它设在**列定义**上，不改动任何 SQL 文本，所以 Gold SQL 原样就能跑出和 MySQL 相同的结果。

**为什么不改 SQL**（比如统一加 `LOWER()`）：那样就修改了标准答案。Phase 0 的原则是原始 Gold 不改，环境差异在环境层解决。

**开关**：`config/phase0.yaml` 的 `environment.collation_policy`。`mirror_mysql_ci`（默认）复刻 MySQL 行为；`binary` 则全部用普通 `STRING`。

**已知局限**（写在 `note` 里）：MySQL `utf8mb4_0900_ai_ci` 中的 `ai` 表示**不区分重音**，`Gödel` = `Godel`；`UTF8_LCASE` 只忽略大小写。Phase 0 核对时，2 张表的 3 列因此有 8 个值差异（如 `tip_material.AUTHOR`）。评测题的 Gold SQL 都没有用到这 3 列，不影响评测。

### 映射结果在哪里被用到

复制每张表时（[benchmark/beaver/phase0.py:94](../benchmark/beaver/phase0.py#L94) `replicate_databases`）用了 4 次：

```
maps = [map_column(c, policy) for c in mysql_columns(...)]   # 每列一个方案

① write_parquet(...)            按 arrow_type 写 Parquet；stage_value 按 databricks_type 转换值
                                 （零日期转 NULL、TIME 转 HH:MM:SS、unsigned 放宽……）
② create_table_sql(fq, maps)    CREATE OR REPLACE TABLE dw.xxx (DEPARTMENT_NAME STRING COLLATE UTF8_LCASE, ...)
③ insert_from_parquet_sql(...)  INSERT ... SELECT；staged_as_string 的列在这里 CAST 成目标类型
                                 （CAST 时去掉 COLLATE，列定义上的排序规则自动生效）
④ profile_sql(...)              两边各算每列的非空数和不同值个数；COUNT(DISTINCT) 遵循排序规则，
                                 只有 UTF8_LCASE 才能和 MySQL 的 _ci 结果对上
```

第 ④ 步验证了这个设计：如果字符串列没有映射成 `UTF8_LCASE`，大量列的"不同值个数"会和 MySQL 对不上。最终 97 张表中 95 张逐列完全一致，剩下 2 张就是上面的重音差异。

### 面试回答参考

> "把 BEAVER 从 MySQL 搬到 Databricks 时，我没有改标准答案的 SQL，而是在列定义层面复刻 MySQL 的行为：无符号整数放宽一级、DATETIME 用不带时区的类型，最关键的是把 MySQL 不区分大小写的 `_ci` 排序规则映射成 Databricks 的 `UTF8_LCASE`，否则同一条 SQL 的等值比较、去重、分组结果都会不同。复制后逐列比对非空数和不同值个数，97 张表中 95 张完全一致，剩下的差异来自 MySQL 还忽略重音，而评测题没有用到这些列。"

## 疑问 22："严格比较只有 37/100 一致，查出三类方言差异后补上两条规则，最终 89 道可用（原样 46 + 适配 43）"，三类方言差异分别是什么？

### 结论

数字都来自项目保留的原始记录：第一次严格比较 `runs/phase0/03_compatibility_run1_strict.json`，差异分类 `runs/phase0/semantics_classes.json`。

第一次把 100 道 Gold SQL 原样在两个引擎上执行、逐值严格比较：

| 结果 | 题数 |
|---|---|
| 一致（COMPATIBLE） | **37** |
| 能跑，但结果不同（SEMANTICS） | 57 |
| 在 Databricks 上报错（UNKNOWN） | 6 |

逐题查原因，归纳出三类方言差异：

| # | 差异 | 涉及题数 | 现象 | 怎么解决 |
|---|---|---|---|---|
| 1 | **数值的表示精度不同** | 9 | 值相同，只是显示方式不同 | **改比较规则**，不改 SQL |
| 2 | **统计函数的口径不同**（总体 vs 样本） | 37 | 能跑，但标准差、方差结果不同 | **规则一**：`VARIANCE/STD/STDDEV → VAR_POP/STDDEV_POP` |
| 3 | **排名类窗口函数上的 frame 子句** | 5 | Databricks 直接报错 | **规则二**：删掉 frame 子句 |

"三类差异、两条规则"的意思是：**第 1 类不是 SQL 写法的问题，修正比较方法就够了，不需要改写规则。**

### 1. 数值表示精度（9 题）

真实例子 dw_2669，同一行结果：

```
MySQL:      ("Provost's Office", Decimal('1.0000'), 0, 0.0, 436372.0, 0.0)
Databricks: ("Provost's Office", 1.0,               0, 0.0, 436372.0, 0.0)
```

MySQL 的 `AVG` 和除法返回保留 4 位小数的 DECIMAL（`1.0000`、`6.8333`），Databricks 返回双精度浮点数（`1.0`、`6.833333…`）。数值相同，只是表示方式不同，严格比较却判为不一致。

解决：跨引擎比较**按 DECIMAL 自身的小数位比较**（[benchmark/beaver/evaluator.py:149](../benchmark/beaver/evaluator.py#L149) `cross_engine_value_equal`）：Databricks 的值四舍五入到 MySQL 给出的小数位后相等即算一致；两边都是浮点数时允许 1e-6 相对误差。一致的题数从 37 提到 **46**，SQL 一个字没改。

### 2. 统计函数口径（37 题）

真实例子 dw_1970，同一行结果：

```
MySQL:      ('Physics', 63.857862647462824, 712.4752130923064, 109962.78824857363, 331.606375464305)
Databricks: ('Physics', 63.998985167970545, 712.4752130923064, 114961.096805327,   339.05913467318203)
```

平均值相同，标准差和方差不同：MySQL 的 `STDDEV` / `VARIANCE` 是**总体**统计（除以 n），Databricks 同名函数是**样本**统计（除以 n − 1）。这是最大也最隐蔽的一类：SQL 能跑，结果看起来合理，只是数不对。用规则一改写后，最终 **38 道**与 MySQL 一致（含第一次运行时卡住、后来重跑的 dw_4004）。

### 3. 窗口函数的 frame 子句（5 题）

dw_4155、dw_3778、dw_4407、dw_3643、dw_3310 在 Databricks 上直接报错：

```
Window Frame specifiedwindowframe(RowFrame, -2, currentrow$()) must match the required frame ...
```

它们给 `RANK`、`LAG` 这类函数写了 `ROWS BETWEEN ...`：MySQL 会忽略这个子句，Databricks 不允许。用规则二删掉后，5 道全部与 MySQL 一致。

### 合起来：37 → 89

```
严格比较一致           37
+ 第 1 类（改比较规则）  +9   → 原样兼容 46
+ 第 2 类（规则一）     +38
+ 第 3 类（规则二）     +5   → 适配 43
= 可用                  89（PRIMARY）
```

另外 **11 道排除**并逐条记录原因：
- 6 道没有适用规则：结果依赖并列值的排序或日期解析，答案本身不确定；
- 4 道用了规则一但结果仍不同：同时受窗口并列值影响；
- 1 道（dw_1795）是 `UNION` 两边的列排序规则不兼容，属于复制造成的类型问题。

两条改写规则的具体含义、实现方式和"原文不改、改写另存"的做法，见 [benchmark/beaver/adapter.py](../benchmark/beaver/adapter.py) 和 [deep_dive/01_基准与数据底座.md](deep_dive/01_基准与数据底座.md) 第 3.6 节。

### 面试回答参考

> "MySQL 和 Databricks 上严格比较只有 37/100 的标准答案一致。我逐题查原因，分出三类：一是数值表示精度，MySQL 的平均值返回 4 位小数的 DECIMAL，值其实一样，这类改比较方法就行，不动 SQL；二是统计函数口径，MySQL 的 STDDEV 是总体标准差、Databricks 是样本标准差，能跑但数不对，这是最大也最隐蔽的一类；三是排名函数上的窗口 frame，Databricks 直接报错。后两类我只用两条有 MySQL 官方文档依据的规则改写，改写结果另存、原文不动，并且要求改写后跑出的结果和 MySQL 一致。最终 89 道可用，剩下 11 道答案本身不确定，排除并记录原因。"

## 疑问 23：项目的知识库和数仓说明为什么用 JSON 文件而不是 Delta 表？企业级项目应该用哪种形式，为什么？

### 现状：各类知识和 schema 存在哪里

| 资产 | 存放位置 | 是不是表 |
|---|---|---|
| 审核知识（选表偏好、补表提示、关联规则、已验证查询） | Delta `self_healing_text2sql.experience.knowledge_items`（提案在 `experience.proposals`） | ✅ |
| 数仓使用说明 | `runs/knowledge/kb.json`，网页副本 `app/bundle/kb.json` | ❌ JSON |
| 相似题示例库 | 命令行运行时从 `data/beaver/dw/dev.json` 现场构建；网页用 `app/bundle/examples_pool.json.gz` | ❌ JSON |
| Agent 看到的表结构 | `runs/phase1/schema_dw.json`（由 `information_schema.columns` + BEAVER 样例值生成并缓存） | ❌ JSON |
| 真实数据表 | Delta `self_healing_text2sql.dw` 下 97 张表 | ✅（SQL 在这里执行） |
| BEAVER 原始表元数据 | Delta `benchmark.tables_meta` | ✅（存档用，Agent 运行时不读，因为里面是 Oracle 类型） |

### 结论

> **当前决定（2026-10-02，决策 D7）**：暂时继续用文件存储，迁移到 Delta 表记为待优化点，方案见 [CONTEXT_DESIGN.md](CONTEXT_DESIGN.md) F6。

现在用 JSON **不是比较后认为它更好，而是实验阶段的权宜做法**。企业项目里，持续更新、多处共享的知识应该**以 Delta 表为唯一可信来源**，运行时再加载进内存或检索索引；文件只作为构建产物或缓存。

### 为什么现在是 JSON

| 资产 | 出现时间 | 当时的需求 | 用文件的理由 |
|---|---|---|---|
| `schema_dw.json` | Phase 1 基线 | 每次实验用同一份表结构 | 查一次后缓存，实验不依赖 Warehouse 状态，可复现 |
| 相似题示例库 | 提升正确率阶段 | 开发集上对比"固定示例 vs 相似题" | 本来就从本地 BEAVER 文件现场构建 |
| `kb.json` | 外循环第 1 步 | 离线统计一次，开发集对照实验 | 一个文件就是一个固定的知识快照，便于和 LLM 缓存配合复现 |
| **审核知识** | 产品化阶段 | **多人写入、审核、上线、回滚** | 文件做不到 → **一开始就用了 Delta 表** |

分界线是：**实验阶段的资产用了文件，产品阶段的资产用了表**，另外两类一直没有从实验形式迁移过来。

文件在实验阶段的好处：快照稳定（实验期间不会被改动）、加载快（5,508 道示例直接读进内存建索引）、不依赖 Warehouse（Free Edition 的 Warehouse 会自动停止）。到了产品阶段，问题就暴露了：更新 `kb.json` 要重新打包部署 App；网页和命令行各有一份副本，可能不一致；说不清某次回答用的是哪个版本的知识；`dw` 表结构变了，Agent 也不会自动感知。

### 企业级项目应该用哪种形式

**原则：受治理的表做唯一可信来源，运行时加载为适合检索的形式；文件只作为构建产物或缓存。**

| 维度 | JSON 文件 | Delta 表（Unity Catalog） |
|---|---|---|
| 唯一来源 | 每个部署实例各一份，可能不一致 | 所有服务读同一份 |
| 更新上线 | 要重新打包、部署 | 写入新版本，服务按需重新加载 |
| 并发写入 | 无保护 | ACID 事务，外循环、审核人可同时写 |
| 版本和回滚 | 靠文件名或 Git 手工管理 | 版本列、状态列，或 Delta 历史版本（time travel） |
| 权限和审计 | 依赖文件系统 | Unity Catalog 统一授权，读写有记录 |
| 血缘 | 无 | 可追溯"这条知识来自哪批数据、哪次外循环" |
| 可分析 | 难 | 能和 trace 关联：某条知识被用了多少次、用后答对率如何 |
| 规模 | 示例多了加载慢 | 可同步成向量检索索引（Databricks Vector Search 直接从 Delta 表同步） |

**文件仍然合适的场景**：内容小、基本不变、随代码发布的东西，如生成规则、prompt 模板，放在代码和 Git 里；实验期间的快照、本地开发的缓存。

### 落到本项目：建议的分层

| 资产 | 唯一来源 | 运行时形式 | 更新方式 |
|---|---|---|---|
| 规则、prompt 模板 | **代码 / Git**（保持现状） | 代码常量 | 改代码、升 prompt 版本 |
| 表结构 | **Unity Catalog 元数据**：`information_schema` + 表 / 列注释（COMMENT） | 进程内缓存，定时刷新 | 数据团队维护注释；结构变化自动感知 |
| 数仓使用说明 | **Delta 表**（如 `experience.kb_stats`），带 `kb_version` | 启动时加载当前版本到内存 | 外循环批处理写入新版本，切换当前版本即生效 |
| 相似题示例库 | **Delta 表**（如 `experience.example_pool`），带版本 | 内存 BM25 索引；规模大了换向量检索 | 同上；已验证查询直接作为其中的行 |
| 审核知识 | **Delta 表** `experience.knowledge_items`（已是如此） | 每次运行读 active 行 | 审核页批准 / 停用 |

两个配套要求：
1. **可复现**：每次运行把用到的知识版本记进运行元数据（`kb_version`、`example_pool_version`、审核知识条目 id，或 Delta 表版本号）。表在变，但任何一次结果都能还原当时的知识状态。
2. **性能**：不要每道题都查表。服务启动时加载一次，之后定期或收到通知时刷新；审核知识量小，可以继续每次运行读取。

表结构一项与 Databricks Genie 的思路一致：表和列的业务说明写在 Unity Catalog 注释里，由数据团队维护，Agent 读这些注释，比只给列名、类型和样例值能拿到更多业务含义。

**迁移成本不大**：
1. `build_knowledge.py` 和示例库构建改为写 Delta 表，并带版本号；
2. `load_knowledge`、`build_generator_index`、`load_bundle` 改为从表读取（保留文件作为本地开发兜底）；
3. 运行元数据里记录知识版本。

### 面试回答参考

> "项目里审核知识存在 Delta 表，因为它要多人写入、审核、随时上线和回滚；统计出的数仓说明和示例库是实验阶段做的，用 JSON 快照方便在开发集上做可复现的对照实验，后来没迁移。如果按企业级落地，我会让所有会变的知识都以 Unity Catalog 里的 Delta 表为唯一来源，带版本号，运行时加载到内存或向量索引；表结构直接读 Unity Catalog 元数据和列注释；规则和 prompt 这类随代码发布的东西才放在 Git。再把每次回答用到的知识版本记进 trace，这样知识可以随时更新，结果又能复现。"

## 疑问 24：`diagnose.py` 为什么调用 `alias_map` 找出 SQL 用了哪些表，而不是用 `sql_facts`？

### 背景

`agent/sql_analysis.py` 和 `agent/join_graph.py` 是**工具**，只陈述事实（SQL 用了哪些表、表之间可以用哪些键关联），不做判断；`loop_engineer/diagnose.py` 是**决策者**，调用工具，结合报错和表结构，判断"为什么失败、该怎么修"。`sql_analysis.py` 里有两个解析函数：

| 函数 | 返回 |
|---|---|
| `alias_map(sql)`（[agent/sql_analysis.py:93](../agent/sql_analysis.py#L93)） | 别名 → 真实表名，如 `{"sd": "sis_department", "at": "academic_terms"}` |
| `sql_facts(sql, schema)`（[agent/sql_analysis.py:51](../agent/sql_analysis.py#L51)） | 用到的表、(表, 列)、"列 = 列"等值条件、常量、运算类型 |

### 结论

诊断真正需要的信息只有 `alias_map` 能直接提供；`sql_facts` 做的事情更多，却恰好不返回这一项。有三个原因。

### 1. 诊断需要"某个别名指向哪张表"，`sql_facts` 不提供

诊断里"列找不到"的规则（[loop_engineer/diagnose.py:83](../loop_engineer/diagnose.py#L83) `diagnose_by_rules`）：

```python
aliases = alias_map(obs.generated_sql)        # {"sd": "sis_department", "at": "academic_terms", ...}
used = set(aliases.values())                   # ① SQL 用了哪些表
hints = {...,
         "qualifier_table": aliases.get((obs.unresolved_qualifier or "").lower()),   # ② 报错里的别名 sd 指向哪张表
         ...}
in_used = [t for t in owner if t in used]      # 拥有这一列的表，SQL 是否已经用了
```

报错只会说 `` `sd`.`TERM_CODE` cannot be resolved ``，里面是**别名**。要判断"是不是挂错了别名"，必须先知道 `sd` 指哪张表。`sql_facts` 内部虽然也按作用域建了"别名 → 表"的对应，但只用于解析列，**不对外返回**，结果里只有真实表名。

### 2. 输入的 SQL 本来就是错的，越简单的解析越稳

走到这条规则的 SQL 一定执行失败、引用了不存在的列：

- `alias_map`：只解析语法树、列出表节点和别名，不需要表结构，也不检查列是否存在，错误的列引用不影响结果；
- `sql_facts`：还要用表结构做 `qualify`（给未加限定的列补表名）并逐个作用域解析列。错误的列引用解析不出来会被丢弃，`qualify` 本身也可能失败（代码用 try/except 兜底）。做了很多对错误 SQL 没有意义的工作。

### 3. 更轻、依赖更少

| | `alias_map` | `sql_facts` |
|---|---|---|
| 需要表结构 | 不需要 | 需要 `{表: {列: 类型}}` 字典（诊断器手里是 `SchemaCatalog`，还得转换） |
| 计算量 | 一次遍历表节点 | 解析 + 补全限定 + 逐个作用域解析列 + 遍历常量和运算 |

诊断每次失败都会运行，没必要多做这些工作。

### 反过来，`sql_facts` 用在哪里

需要完整结构、做逐项比较时才用：
- **失败标注器**（评测侧，`benchmark/beaver/subtasks.py`）：生成 SQL 与 Gold SQL 逐项比较表、列、关联等值、常量、运算；
- **外循环**（`evaluation/outer_loop.py`）：准确拿到生成 SQL 用了哪些**真实存在的**表，与 Gold 对比找出漏表。

### `alias_map` 的局限

它把所有作用域的别名**合并成一张表**：

```python
for t in tree.find_all(exp.Table):
    out[(t.alias or t.name).lower()] = t.name.lower()   # 同名别名会被后出现的覆盖
```

- 同一个别名在不同子查询 / CTE 里指向不同的表时（例如两个子查询都用 `t`），后出现的会覆盖前面的，诊断可能找错表；`sql_facts` 按作用域分别处理，没有这个问题。
- CTE 名字也会被当成"表"收进去（如 `ranked_subjects`）。对诊断没有影响，因为后续只拿真实表结构里存在的表比较。

实际生成的 SQL 很少跨作用域复用同一别名，所以诊断选择了"简单、稳、刚好够用"的 `alias_map`。如果要处理更复杂的 SQL，可以在 `sql_analysis.py` 加一个"按作用域返回别名映射"的函数，同时解决这两个问题。

### 面试回答参考

> "诊断'列找不到'时，报错里给的是别名，比如 `sd.TERM_CODE`，我需要知道 `sd` 指哪张表、SQL 已经用了哪些表，才能判断是别名挂错还是少用了表。`alias_map` 正好返回别名到表的映射，而且只解析语法树、不依赖表结构，对本来就有错误列引用的 SQL 也很稳。`sql_facts` 会做完整的列解析和补全，适合评测时和标准答案逐项比较，但它不返回别名映射，对诊断来说既多余又更容易受错误 SQL 影响。代价是 `alias_map` 不区分作用域，同名别名会互相覆盖，这是一个已知的局限。"

### 定义

[loop_engineer/observer.py:15](../loop_engineer/observer.py#L15)：

```python
OBSERVABLE_FIELDS = ("case_id", "attempt_id", "question", "retrieved_tables", "generated_sql", "parse_status",
                     "execution_status", "execution_error", "result_row_count", "result_preview",
                     "verifier_signals", "verifier_findings")
```

### 12 个字段（按 Loop 的步骤分四组）

| # | 字段 | 含义 | 由谁写入 | 例子 |
|---|---|---|---|---|
| **题目** | | | | |
| 1 | `case_id` | 题目编号 | 控制器 | `dw:dw_2277` |
| 2 | `attempt_id` | 第几次尝试 | 控制器 | `1` |

| 5 | `generated_sql` | 这次的 SQL | 生成或修复 | `WITH ranked_subjects AS (SELECT …)` |

| 9 | `result_row_count` | 返回行数 | 执行 | `35`；未执行成功时为空 |
| 10 | `result_preview` | 结果前 5 行（规范化 JSON） | 执行 | `[["Mathematics", "18.03", 12], …]` |
| **自检** | | | | |
| 11 | `verifier_signals` | 自检不通过的原因 | 自检 | `["execution_error"]`、`["join_tautology"]` |
| 12 | `verifier_findings` | 触发不通过的检查详情：证据和给修复用的提示 | 自检 | `[{"signal": "join_tautology", "evidence": {"condition": "sd.X = sd.X"}, "hint": …}]` |

**共同点**：都是系统**在运行时自己就能拿到**的信息：题目、自己写的 SQL、数据库的返回、自检的结论。生产环境里没有标准答案，系统同样能拿到这些。

### 被挡在外面的字段

尝试记录里还有很多字段不在白名单里，`observe` 会直接丢弃：

| 类别 | 例子 | 为什么挡掉 |
|---|---|---|
| **由 Gold 算出的** | `correct`（是否答对）、`eval_message`、`eval_table_recall`（表召回率） | 运行时不应知道答案对不对；混进来就等于诊断在看答案 |
| 题目元数据 | `category`（题目类别） | 来自基准标注，生产环境没有 |
| 与诊断无关的 | token、耗时、模型名、`strategy` | 不是失败原因的证据 |
| 上一轮的诊断和修复字段 | `failure_type`、`repair_skill` 等 | 每次失败都重新诊断，不沿用上一轮结论 |

**为什么用白名单而不是黑名单**：黑名单要列出"哪些不能看"，以后新增一个由 Gold 算出的字段，忘了加进黑名单就会泄露；白名单只列"哪些能看"，新字段默认进不来。测试专门检查：带有 `correct`、`eval_*` 等字段的记录经过 `observe` 后，这些字段都不会保留（`tests/test_phase4.py` 的 `test_observer_whitelist_blocks_gold_and_correctness`）。

### 12 个字段之外，`Observation` 还多了什么

`observe` 还从报错文本中**解析**出结构化信号，一起放进 `Observation`（用 4 个正则从报错文本中提取，见 [loop_engineer/observer.py](../loop_engineer/observer.py) 的 `observe`）：

| 解析出的字段 | 来自 | 例子 |
|---|---|---|
| `error_class` | `execution_error` 开头的方括号 | `UNRESOLVED_COLUMN` |
| `unresolved_qualifier` / `unresolved_column` | "name … cannot be resolved" | `ccso` / `NUM_ENROLLED_STUDENTS` |
| `suggestions` | "Did you mean …" | `("ccso.GRADE_RULE_DESC", …)` |
| `missing_table` | "table or view … cannot be found" | `school` |
| `db` | `observe` 的第二个参数 | `dw` |

这些都是从白名单字段（主要是 `execution_error`）**推导**出来的，没有引入新的信息来源。所以 `Observation` 的全部内容仍然只来自这 12 个字段和库名。

### 面试回答参考

> "诊断和修复只能通过 Observer 看到一次尝试，Observer 用白名单只放行 12 个字段：题目编号、尝试次数、问题、给模型看的表、SQL、能否抽出 SQL、执行状态、报错、行数、前 5 行结果，以及自检的信号和发现。这些都是生产环境里系统自己就有的信息。是否答对、表召回率这类由标准答案算出的字段一律进不来。用白名单而不是黑名单，是因为以后新增字段时默认不可见，不会因为忘了屏蔽而泄露答案，测试里也专门验证了这一点。"

## 疑问 26：是否可以这样理解——基础信号评估语法错误，`TRIGGER_SIGNALS` 评估语义错误；先用基础信号拦截，再用语义信号拦截，最后失败的去诊断是哪一类错误（`TRIGGER_SIGNALS`）？

### 结论

大方向对：**先拦显式失败，再拦语义问题，没通过的交给诊断**。但有三处需要修正。

> 背景：自检的信号定义在 [loop_engineer/verifier.py:23](../loop_engineer/verifier.py#L23)：`SELF_SIGNALS = BASIC_SIGNALS + TRIGGER_SIGNALS`；`TRIGGER_SIGNALS` 定义在 [loop_engineer/checks.py:48](../loop_engineer/checks.py#L48)。

### 修正 1：基础信号不只是语法错误

基础信号拦的是**显式失败**，也就是不用理解题意就能看出来的失败：

| 基础信号 | 拦什么 | 是不是语法错误 |
|---|---|---|
| `no_sql` | 模型没写出 SQL | 不是 |
| `execution_error` | **所有**执行报错：语法错误、列不存在、表不存在、类型不匹配、超时、被拒绝执行 | 部分是 |
| `too_many_rows` | 结果超过 50 万行（多半是关联写错导致爆炸） | 不是，SQL 能跑 |
| `empty_result` | 结果为空 | 不是，SQL 能跑 |
| `all_null_column` | 某一列全是 NULL | 不是，SQL 能跑 |

后三个都是 SQL **能跑**、但结果明显不对。

### 修正 2：语义信号只覆盖一小部分语义错误

`TRIGGER_SIGNALS` 只有 10 条：4 条结构规则（关联条件恒为真、JOIN 无条件、缺少分组、四舍五入要求不符）+ 6 条数值规则（统计量之间必然成立的关系）。只有它们在离线评估中**误报接近 0**，才被允许触发修复。

- 误报较高的语义检查（重复行、输出列数、题干中的值缺失等）也会运行，但结果只作为"提示"显示，不判为不通过；
- 大部分语义错误**拦不住**：选错相似表、关联路径不对、过滤口径理解错。这些 SQL 能跑、结果看起来正常，会**通过自检**，循环直接结束，根本到不了诊断，要靠外循环补知识。

### 修正 3：诊断判断的是"失败类型"，不是 `TRIGGER_SIGNALS`

`TRIGGER_SIGNALS` 是**自检**的结论，是诊断的**输入**之一；诊断的输出是另一套分类：6 种失败类型（选表、列映射、关联键、领域知识、查询拆解、执行错误），用来决定交给哪个修复技能。**两种信号拦下的失败都会进入诊断**，诊断按拦截原因用不同证据判断：

| 被哪种信号拦下 | 诊断看什么 | 例子 |
|---|---|---|
| 基础信号：报错类 | 报错中的**错误类别**和列名、表名 | 列找不到 → 查列属于哪张表 → 列映射或选表 |
| 基础信号：结果过大 | 执行状态 | → 关联键 |
| **语义信号** | 自检的**发现**，按映射表归类 | 关联条件恒为真 → 关联键 |
| 基础信号：结果为空、某列全空（以及超时、被拒绝） | 没有可用的规则证据 | → 交给 **LLM** 推断 |

为此，Observer 白名单**同时保留**报错原文（`execution_error`，给报错类失败用）和自检结论（`verifier_signals`、`verifier_findings`，给语义类失败用）。

### 修正后的完整理解

```
SQL 执行完
  │
  ├─ ① 基础信号（显式失败）：没 SQL / 报错 / 行数爆炸 / 结果为空 / 某列全空
  │      └─ 命中 → 不通过（语义检查不再运行）
  │
  ├─ ② 语义信号 TRIGGER_SIGNALS（只在 SQL 能跑且有正常结果时运行）：
  │      4 条结构规则 + 6 条数值规则
  │      ├─ 命中 → 不通过
  │      └─ 其他语义检查 → 只作提示，不影响结果
  │
  ├─ 都没命中 → 自检通过 → 结束（可能仍然答错，自检发现不了）
  │
  └─ 不通过 → 观察 → 诊断：判断属于 6 种失败类型中的哪一种
                 ├─ 报错类      → 看错误类别（规则）
                 ├─ 语义信号类  → 看自检的发现（规则，映射表）
                 └─ 结果为空等  → 交给 LLM
              → 路由到对应的修复技能 → 修复 → 再执行
```

一句话概括：**自检负责"拦"，分两层：先拦显式失败，再拦少数可靠的语义问题；诊断负责"判"，对拦下来的所有失败判断原因，决定怎么修。** 能通过自检的错误答案，内循环无能为力，要靠外循环。

### 面试回答参考

> "自检分两层拦截：第一层是显式失败，没写出 SQL、执行报错、结果爆炸、结果为空、某列全空，不用理解题意就能判断；第二层是 10 条语义检查，包括结构规则和用代码核对的数值一致性，只有离线评估误报接近 0 的才允许触发修复，其他只作提示。拦下来的失败交给诊断，诊断再判断属于 6 种失败类型中的哪一种：报错类看数据库的错误类别，语义类看自检的发现，都是规则；只有结果为空这类没有具体证据的才问 LLM。选错表这类能跑、结果也像样的错误，自检拦不住，是外循环要解决的。"

## 疑问 27：项目里 context 指"每次调用 LLM 时送进去的全部内容"，context 在 Agent 项目中的本意是什么？

### 结论

项目的定义是**技术层面**的说法，本身没错，对应 Agent 领域"上下文窗口"的含义。在 Agent 领域，context 通常有三层含义，本项目都有对应（详见 [CONTEXT_DESIGN.md](CONTEXT_DESIGN.md) 第 1.1 节）。

### 1. 上下文窗口：模型这一次能看到的全部内容

大模型本身**没有记忆**，每次调用都只依据这一次送进去的内容作答，长度受 token 上限约束。典型 Agent 一次调用的 context 包括：

| 组成 | 说明 |
|---|---|
| 系统提示 / 指令 | 角色、规则、输出格式 |
| 工具定义 | 有哪些工具可调用、参数是什么（使用 function calling 时） |
| 对话历史 | 之前的多轮消息 |
| 工具调用结果 | 上一步工具返回的数据、报错 |
| 检索到的资料 | RAG 检索出的文档、示例 |
| 记忆 | 从长期存储取回的偏好、历史经验 |
| 当前任务 | 这一次的问题 |

### 2. Agent 的信息状态：完成任务所需的全部信息

Agent 多步运行：调用模型、执行动作、观察结果、再调用模型。完成任务所需的信息存放在模型之外，**每一步挑选其中一部分写进这一次的输入**：

| 类别 | 含义 | 本项目对应 |
|---|---|---|
| 短期记忆 / 工作记忆 | 当前任务过程中产生的信息 | 尝试记录：上次的 SQL、报错、自检发现、诊断 |
| 长期记忆 / 知识 | 跨任务积累、可复用的信息 | 示例库、数仓使用说明、审核知识 |
| 环境信息 | 外部世界的事实 | 表结构、数据库执行结果 |

### 3. 上下文工程：每一步给模型看什么

Agent 的效果很大程度上取决于每一步给模型看了什么，于是有了"上下文工程"的说法：

| 问题 | 含义 | 本项目的做法 |
|---|---|---|
| 选什么 | 从大量信息中挑出与当前步骤相关的 | BM25 选 20 张表、相似题取 4 道、说明按题取相关几行、审核知识按条件触发 |
| 怎么压缩 | 长内容截断、摘要 | 报错 ≤ 1,200 字、结果只给前 5 行、每列样例 ≤ 3 个 |
| 怎么排列 | 重要的放在哪里 | 规则在前、审核知识先于统计说明、示例紧挨问题 |
| 怎么隔离 | 不该看的不给看；不同步骤各用各的 context | Observer 白名单挡住标准答案；生成、诊断、修复各自组装 prompt |
| 写到哪里 | 产生的信息存到哪里、以后再取 | 尝试记录写进 trace；外循环把知识写进知识库 |

### 本项目与典型 Agent 的差别

| | 典型的工具调用式 Agent | 本项目 |
|---|---|---|
| 谁决定下一步做什么 | **模型**决定调用哪个工具 | **代码**（控制器）按固定顺序决定 |
| 工具定义是否进 context | 是 | 否：执行、检索、诊断都由代码直接调用 |
| 上一步的信息怎么传给下一步 | 通过不断累积的对话历史 | 由代码挑选需要的部分，**重新写进**下一次的 prompt |

本项目更接近**由代码编排、在若干步骤调用 LLM 的工作流**。好处：每次调用的 context 完全确定、可复现、可缓存；每一步看到什么可以精确控制（诊断和修复看不到标准答案）；成本不会随步骤增加而膨胀。代价是灵活性：模型不能自己决定"再查一下数据库确认一个值"。之前评估的"查库验证子 Agent"（`validators.py`）就是朝"让 Agent 自己调工具"方向的尝试。

### 面试回答参考

> "context 最基本的含义是模型这一次能看到的全部内容，因为大模型本身没有记忆。往上一层，是 Agent 完成任务所需的信息状态：短期记忆是任务过程中产生的信息，长期记忆是跨任务积累的知识，它们都存在模型之外，每一步挑一部分写进输入；决定选什么、怎么压缩、怎么排列、怎么隔离，就是上下文工程。在我的项目里，短期记忆是每次尝试的记录，长期记忆是示例库、数仓说明和审核过的知识；Loop 由代码编排，每一步由代码挑选信息重新拼 prompt，所以 context 完全可控、可复现，诊断和修复也看不到标准答案。"

## 疑问 28："导入限制：修复技能、诊断、Policy、Observer 不能 import benchmark / evaluation（测试强制）"是什么意思？

### 结论

**在代码层面禁止运行时处理失败的组件接触标准答案，并由自动化测试保证，而不是靠人自觉。**

### 为什么要限制

两个包存放着**含有标准答案（Gold）的代码**：

| 包 | Gold 相关内容 |
|---|---|
| `benchmark/` | `BeaverCase`（带 `gold_sql`、标注的表、关联键、领域知识）；失败标注器 `label_failure`；Gold 结果的冻结与比较 |
| `evaluation/` | 判分器；开发集（含 MySQL 上算出的 Gold 行）；干预实验（把 Gold 提示写进 prompt） |

修复技能、诊断、Policy、Observer 是 Loop 在运行时处理失败的组件，只应看到 Agent 自己能观察到的信息。其中任何一个文件导入了这两个包，就**有能力**拿到标准答案；哪怕是为了图方便调用一个工具函数，也可能让诊断或修复"偷看答案"。线上没有标准答案，系统的真实能力会因此被高估，实验结果作废。

### 测试怎么检查

[tests/test_phase5.py:136](../tests/test_phase5.py#L136)：

```python
@pytest.mark.parametrize("path", sorted(Path("skills").glob("*.py")) + [Path("loop_engineer/policy.py"),
                                                                       Path("loop_engineer/diagnose.py"),
                                                                       Path("loop_engineer/observer.py")])
def test_loop_components_never_import_gold_or_evaluation(path):
    tree = ast.parse(path.read_text(encoding="utf-8"))          # 把源码解析成语法树（不执行代码）
    mods = {n.module for n in ast.walk(tree) if isinstance(n, ast.ImportFrom) and n.module} | \
           {a.name for n in ast.walk(tree) if isinstance(n, ast.Import) for a in n.names}   # 收集所有 import 的模块名
    assert not any(m.startswith(("benchmark", "evaluation")) for m in mods), (path, mods)
```

1. **检查哪些文件**：`skills/` 下所有文件，加上 `policy.py`、`diagnose.py`、`observer.py`；
2. **怎么检查**：用 Python 的 `ast` 模块把源码解析成语法树，找出所有 `import xxx` 和 `from xxx import ...`，包括写在函数内部的；
3. **判定**：任何一个模块名以 `benchmark` 或 `evaluation` 开头，测试就失败，并打印出文件和导入的模块。

以后有人在技能里加一句 `from evaluation.devset import ...`，运行 `pytest` 就会立刻报错，不会悄悄混进去。

它是 Gold 隔离的三道防线之一：

| 防线 | 挡住什么 | 位置 |
|---|---|---|
| `AgentTask` | Agent 只收到题号、问题、库名，**数据**层面拿不到 Gold | `benchmark/beaver/dataset.py` |
| Observer 白名单 | 诊断和修复只能看到 12 个字段，**运行时数据**进不来 | `loop_engineer/observer.py` |
| **导入限制** | 这些组件的**代码**本身就引用不到 Gold 相关模块 | `tests/test_phase5.py` |

### 需要知道的两个细节

**1. 限制只覆盖处理失败的组件，不是所有运行时代码。** 有几个运行时文件确实从 `benchmark` 导入了东西，但导入的都**不含 Gold**：

| 文件 | 导入了什么 | 是否含 Gold |
|---|---|---|
| `controller.py`、`generator.py` | `AgentTask`：只有题号、问题、库名的类型 | 否 |
| `generator.py`、`examples.py`、`knowledge.py` | `apply_rules`：Phase 0 的方言改写规则 | 否 |
| `controller.py` | `serialize_rows`：把结果行转成 JSON 的格式化函数 | 否 |

这说明限制是**按包名**划分，而不是按"有没有 Gold"划分：`benchmark` 包里同时放了含 Gold 的代码和不含 Gold 的通用工具。更干净的做法是把这几个中立工具移到单独的包（如 `AgentTask` 移到 `agent/`，`apply_rules`、`serialize_rows` 移到公共模块），这样导入限制就能扩大到所有运行时代码，控制器、生成器、知识模块也一并纳入检查。

**2. 这是静态检查，能被刻意绕过。** 它只检查源码里写明的 import 语句；用 `importlib.import_module("evaluation.devset")` 这类动态导入就发现不了。所以它防的是"无意中引用"，不是"刻意绕过"，后者要靠代码评审。

### 面试回答参考

> "Gold 隔离我做了三道防线：数据上，Agent 只拿到题号、问题和库名；运行时，诊断和修复只能通过 Observer 白名单看到 12 个字段；代码上，有一个测试用语法树扫描修复技能、诊断、路由和 Observer 的源码，只要导入了存放标准答案和判分逻辑的 benchmark 或 evaluation 包，测试就失败。这样即使以后有人图方便引用了评测代码，CI 也会拦下来。它是按包名限制的，所以下一步是把 AgentTask、方言规则这类中立工具移出 benchmark 包，把检查扩大到所有运行时代码。"

## 疑问 29："开发集平均表召回率 0.92；Gold 用到而生成 SQL 没用的表共 41 次，其中 34 次已经在这 20 张里。瓶颈不在检索，而在下一步选哪张表"是什么意思？

### 结论

这段话解释了**为什么改进重点放在"选表"，而不是"检索"**：标准答案需要的表大多已经给模型看到了，模型是在候选表里选错了。

### 1. 平均表召回率 0.92

生成 SQL 之前，BM25 先从 97 张表里检索出 20 张候选表，只有这 20 张的结构会放进 prompt。

**表召回率** = 标准答案用到的表中，有多少比例出现在这 20 张候选表里。例如标准答案用了 4 张表，3 张在候选里，这道题的召回率就是 3/4 = 0.75。开发集 30 题平均 **0.92**：标准答案需要的表，92% 都已经给模型看到了。

### 2. 41 次里有 34 次已经在这 20 张里

对一次 deepseek 运行（开发集 30 题，最多修复 4 次）的最终答错题逐题比较"标准答案用了哪些表"和"生成的 SQL 用了哪些表"：

- 标准答案用到、但生成的 SQL **没用**的表，共出现 **41 次**（一道题里缺一张表算一次，累计）；
- 其中 **34 次**，这张表**就在给模型看的 20 张候选表里**：模型看到了，但没选它；
- 只有 **7 次**是这张表不在候选里，模型没机会看到。

缺表的情况中，83%（34/41）是"看到了没选对"，只有 17% 是"没检索到"。

### 3. 瓶颈在选表

| 如果瓶颈在…… | 应该怎么改 | 最多能解决 |
|---|---|---|
| 检索 | 多检索几张表、换更好的检索方法 | 那 7 次 |
| **选表** | 帮模型在候选表里做出正确选择 | **那 34 次** |

模型为什么会选错：这个数仓里有很多名字和列都很像的表，例如 `subject_offered`、`subject_offered_summary`、`tip_subject_offered`、`library_subject_offered` 都有选课人数这类列。只看表结构，模型分不清"这类问题在这个数仓里习惯用哪张"。

这个结论直接决定了后续的改进方向：
- **相似题示例**：检索和新问题最像的已解题，告诉模型同类问题用的是哪些表。开发集上 glm 答对 0 → 3；
- **数仓使用说明**：统计"问题里出现某个词时通常用哪些表、相似表之间各占多少比例"。答对 3 → 5；
- **外循环的补表提示和选表偏好**：针对模型反复选错、漏选的表，补充审核过的规则。

没有去做的：把检索从 20 张加到 30 张，或换成向量检索。即使检索做到完美，也只能解决那 7 次。

数据出处：EXECUTION_LOG 的 G.1，运行 `console-targeted-self-20260928T105340-eef1a9`（deepseek-flash，固定示例，开发集 30 题）。

### 面试回答参考

> "我先量化了检索：BM25 取 20 张表，开发集上标准答案需要的表 92% 都在候选里。再看 deepseek 的错题，标准答案用了、模型没用的表有 41 次，其中 34 次模型其实看到了，只是在一堆相似的表里选错了。所以我没有去加大检索范围或换向量检索，那最多只能解决 7 次；而是在生成端补'这个数仓同类问题怎么用表'的知识：相似题示例和从已解题统计的使用说明，glm 在开发集上从 0 题答对提到 5 题。"

## 这些问题带给项目的价值

| 方面 | 价值 |
|---|---|
| **路线选择有依据** | 通用模型 + 上下文工程是企业主流路线；本项目的外循环知识（相似题示例、数仓使用说明）对应企业的"语义层 + 已验证查询库"，方向与工业界一致 |
| **能讲清取舍** | 知道什么时候该微调、什么时候不该，以及两者如何配合，体现工程判断而不只是会调模型 |
| **参数有数据依据** | 检索用 BM25、k=20 都能用召回曲线和题目用表分布解释；并能指出真正的瓶颈在"选对表"而不是"检索到"，决定了改进重点放在生成端 |
| **context 分层清楚** | 结构事实（schema，只读）、通用约定（规则）、经验知识（示例库、使用说明，由外循环更新）、运行时观察（内循环每轮变化）分开管理；外循环只叠加知识、不改结构事实 |
| **能讲清每层设计的分工** | 生成端的三个模块（retriever 找表、examples 给例题、knowledge 给统计规律）各解决一个问题，能对应到错误分析里的具体错因；LLM 调用层的缓存、贪心解码、预算和重试保证实验可复现、成本可控 |
| **数据纪律是加分项** | 训练 / 开发 / 评测三份数据分工明确、做过泄漏检查，比企业常见的"一套基准问题边调边测"更严格，能解释为什么这样做 |
| **看清项目的缺口和定位** | 内循环负责可靠性、外循环负责进化，准确率提升来自外循环；而外循环目前仍是人工流程，下一步要做成"自动提议 + 回归门禁 + 人工批准"的代码化闭环，与企业的评测驱动、人在环路做法一致 |
| **清楚自动检测的边界** | 知道线上只能可靠发现显式错误，语义正确性要靠事前知识（语义层、已验证查询）、用户核对和离线评估；能把项目的内外循环对应到企业"预防、检测、核对、评估"四类手段，并指出可补的方向（多候选一致性、解释理解、主动澄清） |
| **反馈用法有分寸** | 能区分"会话上下文 / 个人经验 / 组织知识"三层，按可信度和作用范围决定反馈何时生效、对谁生效，与市场产品的已验证查询机制一致 |
| **可落地的延伸方向** | ① 平台加"答案有误"反馈，演示线上反馈闭环；② 用训练集做小规模微调，和"通用模型 + 外循环知识"对比效果和成本；③ 评测集持续更新的机制 |
